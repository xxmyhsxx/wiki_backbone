# Skill Creator

## 任务

创建或修改完整的 Skill。README 保存当前设计及关键取舍，SKILL.md 保存执行规范，references 是具体步骤按需使用的可选材料。

## 输入

取得需求和已有材料；修改时读取 README、SKILL 及本次涉及的辅助文件。结合对话判断目标、当前阶段、已确认内容与授权范围，保留用户已有修改。

## 原则

- 设计变化先讨论，经授权写入 README；当前 README 完成且用户确认实现后，再修改 SKILL 或辅助材料。有效授权不重复询问，用户明确要求以其指定方式完成时遵从。
- 仅修正实现以符合已确认设计，或调整不影响设计的文字时，按用户对该修正的明确授权执行，不重写无关设计或重走流程。
- 主动提出具体方案及判断依据，只询问会影响目标、质量、范围、成本或流程的缺口；普通实现细节自主决定。
- 原则保存全程约束，步骤规定操作和判断。必需方法写入 SKILL 或明确引用的随包材料，不依赖未交付的对话结论。
- 用具体对象和动作表达，保留必要条件、例外与不确定性；优先合并、替换或删除重复内容，不为假设需求增加规则或文件。

## 工作步骤

### 1. 确定当前阶段

比较需求、README 与实现，区分：

- 本轮已讨论并写入 README 的变化：属于待同步设计，按当前实现授权继续，不误报为冲突。
- 用户已明确指出并授权的实现修正：按该范围处理，不重新询问已裁决的问题。
- 无法根据已确认信息解释的冲突：说明具体差异并询问，不自行选择版本。

缺少 README 时，说明缺失，基于现有实现提出待确认的设计理解；经讨论和授权补写，再按确认实现。不能把反推结果当作已确认设计。

需要设计时进入第 2 步；设计已明确则进入第 3 步；当前 README 与实现授权均具备时进入第 4 步。仅文字或实现修正沿用已有设计，直接处理相应文件。

### 2. 理解任务并确定设计

说明任务要交付什么、哪些关键问题影响结果、质量依据什么判断，以及候选方法何时采用、怎样检查效果。分析到足以确定关键动作即可，不只列阶段名称或“提高质量”等口号，不编造量化阈值。

先给方案、推荐理由和取舍，再询问真正影响设计的未知信息。检查边界、输入、原则、步骤、输出、辅助材料和校验是否完整，不把这些维度变成用户问卷。

核对质量目标是否实际影响动作、判断或检查方式。例如，算子优化可要求每轮先与参考实现比较正确性，再比较性能；其他任务采用自身适用的方法，不套用该例。

重要不确定性解决后结束讨论，修改任务保留未受影响的设计。这一步不写文件。

### 3. 写入当前设计

已有 README 写入授权时，按讨论结果创建或修改 README；没有时请求授权。默认使用以下结构，没有实际内容的可选部分可省略：

```markdown
# <Skill Name>

## 1. 任务与设计目标
## 2. 使用边界
## 3. 输入设计
## 4. 原则设计
## 5. 工作流程设计
## 6. 输出设计
## 7. References 设计（可选）
## 8. 校验设计
## 9. 文件结构
```

设计写清关键方法及理由，流程与校验体现其用途。只保存当前设计，不默认写修改历史、讨论记录或独立计划文件。

完成 README 后，检查是否已有针对当前设计的实现授权；有则继续，没有则请用户确认按当前 README 实现。后续新增设计变化另按对应授权处理。

### 4. 实现完整 Skill

将已确认设计转成执行指令：关键步骤写清依据什么信息、采取什么动作或判断、形成什么结果。只在影响执行时补充分支，不强制每步使用相同字段。

SKILL 默认结构：

```markdown
---
name: <skill-name>
description: "说明用途和使用时机。"
---

# <Skill Name>

## 任务
## 输入
## 原则
## 工作步骤
## 输出
## 校验
```

替换占位符。name 与目录名一致，使用 1–64 个小写英文字母、数字或连字符，不以连字符开头或结尾，也不含连续连字符；description 为 1–1024 字符的非空字符串。不强制其他元数据，另有已确认的平台要求时遵从。

辅助材料只在确有用途时创建、修改或删除，在使用它的步骤说明何时读取及如何使用，不默认全部加载。必需方法随 Skill 交付，不能仅引用未提供的对话。发现需要改变已确认设计时，先说明影响并讨论。

### 5. 检查并交付

对照设计与实际差异，检查方法遗漏、执行矛盾、步骤衔接、输出、元数据、占位符和文件引用。确认未覆盖无关改动，references 有具体用途。

逐段检查表达：删掉后不影响理解、判断或行动的内容就删；对象、动作或指代需要猜的句子改清楚。全程约束放在原则，具体动作放在对应步骤，校验关注如何确认结果，避免反复抄写同一要求。删减后核对条件、例外、权限与必要方法仍完整。

按改动选择代表性输入，沿关键步骤检查信息、判断依据、衔接及结果。必要时检查重要失败分支。优先使用用户材料；构造案例注明性质。可选场景包括模糊需求、仅认可方案、只授权 README、确认后续接、局部修改、缺少 README 和设计冲突，不要求每轮全部执行。

静态检查和推演指出支持判断的规则；真实运行必须有实际输出或工具结果。条件与授权不足时说明限制，不以推演冒充运行通过，不默认建立自动评分器或独立测试目录。

范围内的实现、格式或引用错误修正后复查；涉及设计变化时先讨论。仅在 README 阶段时检查设计，不提前同步实现。

## 输出

按当前阶段交付方案、README 或完整 Skill，说明实际改动、检查结果和未验证部分。需要确认时说明具体未决选择或授权缺口，不重复索取有效授权。

## 校验

- 当前阶段与授权相符，局部修改未扩大范围。
- 关键方法已落实为可执行动作，README 与实现一致；尚未同步时明确状态。
- 表达清楚且必要，删减保留条件、例外和判断依据。
- 元数据、引用与随包材料可用，必要场景按范围检查。
- 静态检查、场景推演与真实运行的结果分别说明。
