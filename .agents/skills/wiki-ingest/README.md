# Wiki Ingest

当前设计由 [SKILL.md](SKILL.md) 执行。

## 1. 任务与设计目标

以 Wiki 的目的为起点，读取用户指定的来源，将有用且有依据的知识整合到 Wiki。用途和读者要求决定整理什么、解释到什么程度；实际材料提供依据；已有知识决定补充、修正或新建哪些页面。

本模板保留通用四步框架。具体 Wiki 的入库说明与 Skill 由 [wiki-init](../wiki-init/SKILL.md) 根据目的、材料类型和页面设计定制，日常入库沿用定制后的流程。

交付的知识应能独立阅读、回查来源，并与已有内容建立必要联系。复用已经充分的内容，避免重复建页。

## 2. 使用边界

用户要求入库、解读并写入资料，或用新来源补充已有 Wiki 时使用。只要求讨论或拟稿时交付具体草稿及落点；仅查询使用 [wiki-query](../wiki-query/SKILL.md)，审核使用 [wiki-review](../wiki-review/SKILL.md)。

接受用户已确认的文章、网页、论文、书籍、视频、音频、图像、代码等来源，按实际读取能力确定可用范围。初始化完成后，介绍与规范 README、AGENTS 及 Skill 文件保持固定；日常入库维护来源及其条目说明、知识、附件、INDEX 与 SELF 的当前状态，并向根目录 `LOG.md` 追加短记录，不自动改变 SELF 中的用途与范围。

关键约定缺失或新材料需要调整流程时，说明具体缺口、建议及影响，继续不受影响的部分，不自动调用 init 或修改规范。用户明确要求调整约定时，再使用 [wiki-init](../wiki-init/SKILL.md)；涉及 Skill 变更时使用 [skill-creator](../skill-creator/SKILL.md)。新来源类型的保存方式可为本次条目确定，记录在条目说明中，不隐含更新长期规范。来源条目 README 是元数据，按资料保存需要创建和维护，不因同名而当作固定规范。

## 3. 输入设计

输入包括目标 Wiki、来源、实际版本或获取信息，以及用户本次的关注问题和写入范围。读取目标已定制的入库流程，并结合 SELF 和知识页面规范执行；没有额外关注点时沿用既定的整理重点与深度。

## 4. 原则设计

1. 以 Wiki 的目的选择内容与解释深度，沿用已确定的约定。
2. 保留原始资料及版本，区分来源陈述、整理者解释与实际验证，条件随结论保留。
3. 阅读正文后判断已有覆盖，复用有效内容，保留有依据的分歧；搜索命中或读取失败不能代替核查。
4. 写入前按文件职责确认范围，沿用固定的介绍与规范；已明确的内容写入自主完成，长期约定的调整以用户明确要求为准。

## 5. 工作流程设计

1. **看 Wiki 的目的。** 读取目标的入库约定、SELF、来源规则及知识页面规范，沿用初始化确定的用途、范围、读者要求和具体做法，判断本次材料中哪些知识有用。按文件职责区分固定的介绍与规范和本次可维护的来源条目、知识、附件、INDEX、SELF 当前状态及只追加的根目录 `LOG.md`；保留固定文件的任务开始状态，供交付前核对。
2. **围绕目的读材料。** 核对来源身份、版本和实际可读范围，理解与用途相关的问题、机制或步骤、例子及限制，保留可回查的依据。必要时查看原始图表、公式或代码；无法读取的关键内容如实说明。
3. **整合进 Wiki。** 读取相关页面，按实际缺口补充、修正或新建内容，保留条件差异和来源分歧，维护必要引用、链接、INDEX；覆盖、缺口或下一步变化时更新 SELF 的当前状态，保留既定用途与范围。按已确认形式将原件、`article.md` 和条目 `README.md` 保存到 `raw/YYYY-MM-DD/条目名称/`；同一来源、同一版本重复处理时复用已有归档，保留原日期及已引用版本。新来源类型尚无保存约定时，为本次条目确定可执行的原件与转录形式；有重要取舍时先与用户确定本次选择，交代实际限制，不修改长期规范。

   知识正文、来源归档和引用分别判断。已有解释充分且没有知识增量时保持正文；不同的新来源即使重复了已有解释，也按约定保存，确实增加证据或澄清出处时只补必要引用。

   核心定义、条件或结论改变后，用名称、别名和相关表述查找 Wiki，读取候选正文与必要链接，只修订直接受影响的内容；条件不同的结论分别保留。
4. **检查并交付。** 从更新后的入口核对内容是否服务于 Wiki 的目的、解释是否清楚、来源是否支持表述。raw 只做位置、三部分齐全且可读、来源清楚的基础检查，关键引用按需回查原件。使用 [wiki-lint](../wiki-lint/SKILL.md) 按约定检查受影响页面及关联，复用有效核验结果。对照任务开始状态核对日常入库没有自动修改固定介绍与规范或 SELF 的用途与范围；同次任务有明确的约定调整要求时，另行核对对应改动是否符合授权范围。发现越界时只修正本次产生的改动，保留用户已有修改。交付归档、正文和引用各自的实际结果，说明实际更新的页面、重要关联页无需修改的原因，以及查找受限和未完成部分；不要求另建永久影响清单。

   实际入库任务结束时，按日期向根目录 `LOG.md` 追加一条短记录，说明做了什么和实际结果，必要时补充原因或未完成项；重复来源或没有知识增量也记录处理结论。只讨论或拟稿不记，本任务内的 lint/review 检查汇总到这一条，不由子 Skill 重复记录。只追加、不改旧条目，具体文件差异交由 Git。

## 6. 输出设计

交付实际新增或修订的页面、来源及必要关联，简要说明补充了什么、页面位置、检查范围和未完成部分。不强制产生入库报告或固定数量页面。

| 评估项 | 完成条件与证据 |
| --- | --- |
| 来源可靠定位 | 实际使用材料、版本及可读范围明确，关键依据可回查。 |
| 内容服务于目的 | 选材与深度符合用途和读者要求，依据已有正文补足缺口或澄清分歧。 |
| 解释可独立使用 | 读者能沿正文及有效链接理解问题、关键机制或步骤、条件和证据边界。 |
| 维护与声明一致 | 必要引用、链接和导航已核对；固定介绍与规范、SELF 用途与范围未被日常入库自动改动，明确要求的约定调整另按授权范围核对；实际写入、草稿及未核验部分分别说明。 |

无需修改时，实际复核已有内容充分也可以完成；材料核心部分不可读或关键解释仍断裂时交付部分结果。

## 7. References 设计

复用目标 Wiki 的规范和实际页面；机械检查复用兄弟 Skill 的脚本。本 Skill 不增加独立解析或检索工具。

LLM Wiki 的来源整合与持续修订思路参考 [Karpathy 原始说明](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)，具体流程依据本项目的用途与来源约定确定。

## 8. 校验设计

检查设计与执行是否一致、四步是否衔接、引用是否可定位。核对 init 已将具体做法落实到目标 ingest 文件，日常入库能沿用这些固定约定；不同用途的定制应体现选材、深度和页面落点的差异。按改动需要补查同一来源同版本重复处理、新来源无知识增量、定义或条件变更、来源冲突、部分可读、新来源类型、关键约定缺失和只要求拟稿等场景。核对来源条目 README 能正常创建，新类型的本次保存选择没有隐含更新规范，固定文件与 SELF 用途、范围未被日常入库自动修改；同次任务明确要求调整时，对应改动仍须符合授权范围。

三部分未齐全时如实报告，重复处理不迁移旧归档。内容核验、机械检查、场景推演和实际运行分别说明。
