# Wiki Init

状态：设计已确认，执行规范已按本设计同步。初始化流程由 [SKILL.md](SKILL.md) 执行。

## 1. 任务与设计目标

基于通用 LLM Wiki 模板，主动引导用户明确用途、范围和组织方式，完成用户自己的 Wiki 初始化。交付后，用户和新进入的 Agent 能从文件中理解 Wiki 的目的、内容边界、知识质量要求、当前内容、工作方式和下一步。初始化依据明确的评估指标验收，结论附有可定位的依据。

关键问题及处理方法：

| 关键问题 | 为什么影响结果 | 方法与质量依据 |
| --- | --- | --- |
| 用户意图不够具体 | 同一主题可能用于学习、比较、研究或实践，组织方式会不同。 | 从实际使用场景或代表性问题澄清用途，方案能够说明知识将如何被使用。 |
| 用户需要帮助判断组织方式 | 直接要求用户给目录，会把设计工作交回用户。 | Agent 先提出推荐方案与理由，讨论影响用途和范围的重要选择，普通实现细节自主决定。 |
| 用户难以判断初始化进展 | 讨论与文件定制可能跨多轮对话。 | 用阶段状态展示实际进展与待定问题，不以文件数量或估计百分比代替完成情况。 |
| 模板没有充分个性化 | 文件存在仍可能保留无关的模板说明或错误描述。 | README、SELF、工作约定和导航共同反映用户已确定的方案及实际内容。 |
| 范围与深度难以判断 | 主题名称不足以判断材料是否收录、页面需要解释到什么程度。 | 用代表性任务和范围内、范围外、边界案例检验约定，解决会改变判断的歧义。 |
| 完成标准不够具体 | 文件已写入时，关键问题仍可能未解决。 | 提前明确验收要求，按七项通用指标检查，交付结论、依据、缺口及下一步。 |

## 2. 使用边界

用户要求创建或初始化 Wiki、在模板副本中定制自己的 Wiki，或补全已有 Wiki 的初始化约定时使用。

本 Skill 负责意图澄清、方案确定、文件定制和核对，并帮助用户确定知识质量要求。已有知识的覆盖、质量及实际运行结果按实际检查另行说明。是否同时处理初始资料，作为本次方案的一部分明确；已有资料可以用于判断组织方式，资料保存与知识建设分别说明。

Skill 的创建和修改由本项目 [skill-creator](../skill-creator/SKILL.md) 指导。日常资料入库、查询和审核按实际任务与可用能力执行；预留的 Skill 不作为已经可调用的能力。

保留目标已有内容和 Git 配置。用户要求配置或发布自己的仓库时，按该项明确请求处理。

## 3. 输入设计

结合对话和目标目录取得：目标位置、用户的用途与主题、内容范围、希望如何使用知识，以及已有资料与文件。能从现有内容判断的信息先读取，不重复要求用户描述。

用户在模板副本中要求初始化当前 Wiki 时，该副本就是目标。要求创建到其他位置时，需要明确目标目录。没有初始资料时仍可初始化结构与约定。

结合读者基础、代表性问题及预期结果判断知识需要解释到什么程度。资料类型、关注问题和维护偏好按实际需要补充；由 Agent 归纳已有信息并提出建议，不要求用户填写固定问卷。

## 4. 原则设计

1. **围绕使用意图深入讨论。** 从实际任务与预期结果出发，逐步澄清用途、边界和知识要求。讨论深度以能否依据约定判断代表性案例为准，已明确的信息直接复用。
2. **主动分析和推荐。** 先提出判断与理由，再讨论重要取舍，不把目录设计全部交给用户。
3. **按已有信息推进。** 已明确的需求和有效授权直接使用；方案明确后连续完成范围内的定制与核对。
4. **依据完成条件更新进度。** 展示当前阶段、已确定事项与待讨论问题。关键缺口解决且本阶段完成条件满足后再更新状态，评估结论附上依据。
5. **保护和复用现有内容。** 修改前读取已有文件，只调整当前方案影响的内容；不改写原始证据，不为分类完整而建立空目录。
6. **状态与实际内容一致。** 区分已保存资料、已形成知识、计划内容与未核验结论；导航指向实际文件。

## 5. 工作流程设计

### 5.1 读取现状，明确意图

读取目标中已有的项目说明、SELF、工作约定及与初始化有关的文件。只补读有助于当前判断的资料。

先整理已明确的用途、范围和已有情况，再询问影响方案的缺口。例如，用户只说要建 Wiki，可以问：

> 你希望这个 Wiki 最先帮你完成什么事？可以举一个以后会向它提出的问题。

用户说明要整理论文后，再根据需要区分学习概念、比较方法或记录实验等用途，并用代表性问题明确预期结果。问题随回答逐步展开；已有信息充分时直接进入方案设计。

本阶段完成时，应能说明目标位置、服务对象、主要用途及代表性任务。影响定位的重要缺口需要解决；其余问题随方案设计继续讨论。

目标位置或会明显影响用途与范围的重要问题尚未明确时，继续讨论可判断的部分，先解决缺口再写入受影响的定制内容。

### 5.2 提出并确定方案

Agent 给出简短的推荐方案，说明用途与范围、来源和知识的组织方式、必要的工作约定、本次会完成哪些内容，以及是否处理初始资料。

解释推荐的理由及重要取舍，根据用户反馈修正。用户已经明确选择时按其选择推进；普通命名、文件组织和链接细节自主处理。

围绕用途逐步明确以下约定，由 Agent 先归纳和推荐，再补问会改变判断的缺口：

- 服务对象、读者基础、主要任务及预期结果。
- 核心内容、相关主题的涉及程度、当前范围之外的内容及理由。
- 主要页面的解释深度和知识质量要求。比较用途关注比较维度、适用条件和证据；实践用途关注前置条件、步骤及结果检查。
- 来源类型、是否允许补充外部资料，以及来源陈述、整理者解释和实际核验的区分方式。
- 入库、查询、审核等工作的输入、输出、写回方式，以及目标实际可用的能力。
- 本轮初始化的交付范围、验收要求、当前内容和下一步。

用代表性任务检验预期结果，用范围内、范围外及边界案例检验收录与解释要求。优先复用用户的问题和资料；没有资料时可构造案例，并说明案例及推演的性质。将发现的重要歧义带回讨论，边界需要扩展时说明影响并按用户明确选择调整。

本阶段完成时，用途、边界、组织方式、知识要求和操作约定应足以指导定制与后续工作。七项通用指标见第 6 节，按用途补充知识质量要求；重要未决问题解决后进入定制。

过程采用以下阶段显示进度：

```text
Wiki 初始化进度
✓ 明确用途与任务
→ 确定边界与工作约定
○ 定制文件
○ 核对与交付
```

示例仅说明展示方式。实际状态依据各阶段完成条件和检查结果更新，可补充已确定与待讨论事项。已完成的阶段直接复用；无需额外建立进度或评估文件。

### 5.3 定制目标文件

在已确定的方案内完成定制。新目录带入所需的模板管理文件、本 Skill 的设计与执行文件，以及实际启用的 Skill 和其依赖；不复制 `.git/`。已有 Wiki 保留有效内容，补齐缺失文件并调整受方案影响的说明与约定。

各文件的职责与定制要求：

- [项目 README](../../../README.md)：说明用户自己的 Wiki 及使用入口。
- [AGENTS](../../../AGENTS.md)：指向目标实际存在的规范与可用 Skill，落实操作及写回约定。
- [来源规则](../../../raw/README.md)：根据资料类型明确保存、版本、外部资料补充和追溯方式。
- [知识页面规范](../../../wiki/README.md)：落实读者基础、解释深度、知识质量、证据与维护要求。
- [SELF](../../../wiki/SELF.md)：记录服务对象、用途、内容边界、实际已有内容、缺口与下一步。
- [INDEX](../../../wiki/INDEX.md)：连接实际存在的管理入口和知识页面。

模板其他管理文件按实际需要保留。携带预留设计时明确其状态，不把它列为可执行 Skill。全部链接按目标中的实际文件核对。

本阶段完成时，已确定的约定应落实到目标文件，README 已适应该用户，SELF 和导航反映实际内容。

### 5.4 核对并交付

依据第 6 节的七项通用指标及本轮知识质量要求检查目标文件。对照方案核对约定，检查文件与链接，并用代表性任务和边界案例检验规则能否指导判断。原有资料、知识和 Git 配置得到保留。

逐项交付结论、可定位的依据、缺口及下一步。文件检查、场景推演与真实运行分别说明；未做达标所需检查时标记“未验证”。

发现缺口时返回相应阶段：定位与边界问题继续讨论，约定遗漏或链接错误在范围内修正，需要改变用途或范围时与用户商量。七项指标均有达标依据后，才能宣布本轮初始化完成。知识建设的后续待办可以保留，现有知识质量及实际运行结果按检查范围另行说明。

交付目标位置、入口、主要定制结果和逐项评估，依据实际完成情况更新进度。

## 6. 输出设计

讨论中交付意图理解、推荐方案、必要问题和本轮验收要求；实施后交付定制后的 Wiki、目标位置、使用入口及逐项评估。

### 6.1 评估指标与验收条件

评估分两层：七项通用指标检查初始化是否完成；按用途确定的知识质量要求指导后续内容建设，并检查这些要求是否已落实。

| 指标 | 达标条件 | 判断依据 |
| --- | --- | --- |
| 用途可执行 | 明确服务对象、主要任务与预期结果，能说明怎样的知识或回答对用户有用。 | 定位说明及代表性问题的预期结果。 |
| 范围可判定 | 明确核心范围、相关主题的涉及程度及当前范围之外的内容，能够处理边界案例。 | 已保存的边界约定及范围内、范围外、边界案例的判断理由。 |
| 深度有依据 | 明确读者基础和主要页面需要解释的内容、深度，要求能够支撑实际用途。 | 知识页面规范及代表性任务对解释要求的检验。 |
| 证据规则可执行 | 明确来源保存、引用与追溯方式，能够区分来源陈述、整理者解释和实际核验。 | 来源与知识页面规范，以及一份来源或构造案例的处理推演。 |
| 操作约定可执行 | 明确入库、查询、审核等工作的输入、输出、写回方式，可用和预留能力状态准确。 | Agent 约定、实际 Skill 文件及典型任务的处理说明。 |
| 文件落实一致 | 文件与导航落实已确定方案，引用有效，原有内容及 Git 配置得到保留。 | 目标文件、链接检查及修改前后的对照。 |
| 后续工作可接续 | 当前内容、缺口与下一步准确，后续 Agent 仅依据保存文件即可说明下一项任务、输入和预期产物。 | SELF、使用入口及依据文件形成的下一步说明。 |

知识质量要求按用途确定。例如，方法比较需要明确比较维度、适用条件和证据要求；操作实践需要明确前置条件、步骤及结果检查。初始化时保存这些要求，已有知识页面是否达到要求按实际核验另行说明。

### 6.2 评估结果与完成标准

每项评估给出结论、依据、缺口及下一步。结论采用：

- **达标**：满足验收条件，有可定位的文件或检查证据。
- **待补齐**：约定缺失或不完整，尚不足以指导工作。
- **未验证**：相关约定已形成，达标所需检查尚未完成。

七项通用指标均有达标依据，影响用途、范围、知识要求和操作方式的关键缺口已解决，且本轮约定的交付已完成，才能宣布本轮初始化完成。没有资料时可通过构造案例推演规则，完成结构与约定的验收；知识覆盖、内容质量和实际运行结果单独说明。

## 7. References 设计

复用仓库现有管理文件，按步骤所需读取。本次不新增独立 References、脚本或进度状态文件。

## 8. 校验设计

静态检查设计与实现是否一致、必需方法是否转化为具体动作、七项评估及阶段完成条件是否落实、文件引用是否可定位，以及输出是否如实区分初始化与知识建设。

按修改范围选取代表性场景检查：需求模糊、需求已明确、没有资料、已有 Wiki、新目标目录或用户只要求讨论。重点观察是否问到影响方案的缺口、是否复用已明确信息、是否在授权范围内定制，以及状态和导航是否与实际内容一致。补查边界案例存在歧义、仅有约定却未做必要检查时，是否继续处理缺口并如实标记评估状态。

文档检查和场景推演分别说明；只有完成实际初始化并检查产物，才能报告真实运行结果。不要求默认建立测试目录或评分器。
