# Wiki Init

状态：设计已确认，执行规范已按本设计同步。初始化流程由 [SKILL.md](SKILL.md) 执行。

## 1. 任务与设计目标

基于通用 LLM Wiki 模板，主动引导用户明确用途、范围和组织方式，完成用户自己的 Wiki 初始化。交付后，用户和新进入的 Agent 能从文件中理解 Wiki 的目的、当前内容、工作方式和下一步。

关键问题及处理方法：

| 关键问题 | 为什么影响结果 | 方法与质量依据 |
| --- | --- | --- |
| 用户意图不够具体 | 同一主题可能用于学习、比较、研究或实践，组织方式会不同。 | 从实际使用场景或代表性问题澄清用途，方案能够说明知识将如何被使用。 |
| 用户需要帮助判断组织方式 | 直接要求用户给目录，会把设计工作交回用户。 | Agent 先提出推荐方案与理由，讨论影响用途和范围的重要选择，普通实现细节自主决定。 |
| 用户难以判断初始化进展 | 讨论与文件定制可能跨多轮对话。 | 用阶段状态展示实际进展与待定问题，不以文件数量或估计百分比代替完成情况。 |
| 模板没有充分个性化 | 文件存在仍可能保留无关的模板说明或错误描述。 | README、SELF、工作约定和导航共同反映用户已确定的方案及实际内容。 |

## 2. 使用边界

用户要求创建或初始化 Wiki、在模板副本中定制自己的 Wiki，或补全已有 Wiki 的初始化约定时使用。

本 Skill 负责意图澄清、方案确定、文件定制和核对。是否同时处理初始资料，作为本次方案的一部分明确；已有资料可以用于判断组织方式，资料保存与知识建设分别说明。

Skill 的创建和修改由本项目 [skill-creator](../skill-creator/SKILL.md) 指导。日常资料入库、查询和审核按实际任务与可用能力执行；预留的 Skill 不作为已经可调用的能力。

保留目标已有内容和 Git 配置。用户要求配置或发布自己的仓库时，按该项明确请求处理。

## 3. 输入设计

结合对话和目标目录取得：目标位置、用户的用途与主题、内容范围、希望如何使用知识，以及已有资料与文件。能从现有内容判断的信息先读取，不重复要求用户描述。

用户在模板副本中要求初始化当前 Wiki 时，该副本就是目标。要求创建到其他位置时，需要明确目标目录。没有初始资料时仍可初始化结构与约定。

读者基础、资料类型、关注问题和维护偏好按实际需要补充，不要求用户填写固定问卷。

## 4. 原则设计

1. **围绕使用意图提问。** 优先问将怎样使用知识、希望解决什么问题；根据回答逐步澄清会改变方案的缺口。
2. **主动分析和推荐。** 先提出判断与理由，再讨论重要取舍，不把目录设计全部交给用户。
3. **按已有信息推进。** 已明确的需求和有效授权直接使用；方案明确后连续完成范围内的定制与核对。
4. **进度反映事实。** 展示当前阶段、已确定事项与待讨论问题，阶段真正完成后再更新状态。
5. **保护和复用现有内容。** 修改前读取已有文件，只调整当前方案影响的内容；不改写原始证据，不为分类完整而建立空目录。
6. **状态与实际内容一致。** 区分已保存资料、已形成知识、计划内容与未核验结论；导航指向实际文件。

## 5. 工作流程设计

### 5.1 读取现状，明确意图

读取目标中已有的项目说明、SELF、工作约定及与初始化有关的文件。只补读有助于当前判断的资料。

先整理已明确的用途、范围和已有情况，再询问影响方案的缺口。例如，用户只说要建 Wiki，可以问：

> 你希望这个 Wiki 最先帮你完成什么事？可以举一个以后会向它提出的问题。

用户说明要整理论文后，再根据需要区分学习概念、比较方法或记录实验等用途。问题随回答逐步展开；已有信息充分时直接进入方案设计。

目标位置或会明显影响用途与范围的重要问题尚未明确时，继续讨论可判断的部分，先解决缺口再写入受影响的定制内容。

### 5.2 提出并确定方案

Agent 给出简短的推荐方案，说明用途与范围、来源和知识的组织方式、必要的工作约定、本次会完成哪些内容，以及是否处理初始资料。

解释推荐的理由及重要取舍，根据用户反馈修正。用户已经明确选择时按其选择推进；普通命名、文件组织和链接细节自主处理。

过程采用以下阶段显示进度：

```text
Wiki 初始化进度
✓ 明确用途与范围
→ 确定组织方式与工作约定
○ 定制文件
○ 核对与交付
```

示例仅说明展示方式。实际状态由已完成的工作决定，可补充已确定与待讨论事项；在关键进展或方向变化时更新，无需额外建立进度文件。已完成的阶段直接复用。

### 5.3 定制目标文件

在已确定的方案内完成定制。新目录带入所需的模板管理文件、本 Skill 的设计与执行文件，以及实际启用的 Skill 和其依赖；不复制 `.git/`。已有 Wiki 保留有效内容，补齐缺失文件并调整受方案影响的说明与约定。

各文件的职责与定制要求：

- [项目 README](../../../README.md)：说明用户自己的 Wiki 及使用入口。
- [AGENTS](../../../AGENTS.md)：指向目标实际存在的规范与可用 Skill。
- [来源规则](../../../raw/README.md)：根据资料类型明确保存、版本和追溯方式。
- [知识页面规范](../../../wiki/README.md)：根据知识组织方式明确页面、解释、引用和维护要求。
- [SELF](../../../wiki/SELF.md)：记录服务对象、用途、范围、实际已有内容、缺口与下一步。
- [INDEX](../../../wiki/INDEX.md)：连接实际存在的管理入口和知识页面。

模板其他管理文件按实际需要保留。携带预留设计时明确其状态，不把它列为可执行 Skill。全部链接按目标中的实际文件核对。

### 5.4 核对并交付

对照方案检查用途、范围、工作约定与实际组织是否一致。确认 README 已适应该用户，SELF 如实记录现状，INDEX 指向真实内容，原有资料、知识和 Git 配置得到保留。

修正范围内的文件、描述和链接问题；需要改变用途或范围的重要问题重新讨论。关键目标尚未确定时如实说明待完成内容，不把部分准备写成整个初始化已经完成。

交付入口、主要定制结果、检查范围、必要遗留问题和下一步。进度显示按实际完成情况更新。

## 6. 输出设计

讨论中交付意图理解、推荐方案及必要问题；实施后交付定制后的 Wiki、目标位置、使用入口和实际核对结果。

结构与约定的初始化完成标准是：用户和后续 Agent 能理解用途、范围、组织方式、实际已有内容及下一步；知识覆盖和核验程度单独说明。

## 7. References 设计

复用仓库现有管理文件，按步骤所需读取。本次不新增独立 References、脚本或进度状态文件。

## 8. 校验设计

静态检查设计与实现是否一致、必需方法是否转化为具体动作、文件引用是否可定位，以及输出是否如实区分初始化与知识建设。

按修改范围选取代表性场景检查：需求模糊、需求已明确、没有资料、已有 Wiki、新目标目录或用户只要求讨论。重点观察是否问到影响方案的缺口、是否复用已明确信息、是否在授权范围内定制，以及状态和导航是否与实际内容一致。

文档检查和场景推演分别说明；只有完成实际初始化并检查产物，才能报告真实运行结果。不要求默认建立测试目录或评分器。
