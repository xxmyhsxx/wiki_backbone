# Wiki Init

状态：设计已确认，执行规范已按本设计同步。初始化流程由 [SKILL.md](SKILL.md) 执行。

## 1. 任务与设计目标

基于通用 LLM Wiki 模板，主动引导用户明确用途、范围和组织方式，完成用户自己的 Wiki 初始化。交付后，用户和新进入的 Agent 能从文件中理解 Wiki 的目的、内容边界、知识质量要求、当前内容、工作方式和下一步。初始化依据明确的评估指标验收，结论附有可定位的依据。

关键问题及处理方法：

| 关键问题 | 为什么影响结果 | 方法与质量依据 |
| --- | --- | --- |
| 用户需求不完整或难以表达 | 逐个字段提问会增加等待，却未必解决关键问题。 | 将可一起回答的问题合并，先给推荐方案和选项，只追问会改变方案的缺口。 |
| 不同项目的判断依据不同 | 未明确依据就设计页面，可能把观点、推测或未验证结果写成事实。 | 按用途识别需要提前明确的证据边界，在页面样例前解决关键缺口；普通资料整理沿用已有引用约定。 |
| 用户不清楚原始材料如何积累 | 只问有没有资料，无法确定后续取得和保存方式。 | 主动推荐资料来源、材料类型及原件、转录的保存形式，再请用户选择或调整。 |
| 用户需要帮助判断组织方式 | 只有目录或虚构样稿，难以判断页面是否有用。 | 尽早读取一份真实材料，用短样稿与目录草案一起检验解释深度、来源和页面关系。 |
| 用户难以判断初始化进展 | 一个总百分比会混淆剩余讨论和实际建库工作。 | 分别显示需求讨论与实际建库的进度，并说明当前环节及剩余事项。 |
| 模板没有充分个性化 | 文件存在仍可能保留无关的模板说明或错误描述。 | README、SELF、工作约定和导航共同反映用户已确定的方案及实际内容。 |
| 查询入口依赖启动目录或模板路径 | 从 Wiki 外使用时可能查错位置，或缺少兄弟 Skill。 | 定制有明确名称与绝对路径绑定的自包含 query，安装同内容镜像，并从独立目录验证。 |
| 范围与深度难以判断 | 主题名称不足以判断材料是否收录、页面需要解释到什么程度。 | 用代表性任务和范围内、范围外、边界案例检验约定，解决会改变判断的歧义。 |
| 完成标准不够具体 | 文件已写入时，关键问题仍可能未解决。 | 提前明确验收要求，按七项通用指标检查，交付结论、依据、缺口及下一步。 |

## 2. 使用边界

用户要求创建或初始化 Wiki、在模板副本中定制自己的 Wiki，或明确要求补全、调整已有 Wiki 的初始化约定时使用。

本 Skill 负责意图澄清、方案确定、文件定制和核对，包括按 Wiki 的目的、材料类型和页面设计定制 ingest，以及定制并安装绑定该 Wiki 的 query。通用 ingest 提供四步框架，日常入库执行定制后的流程。是否同时处理初始资料，作为本次方案的一部分明确；已有知识的覆盖、质量及实际运行结果按实际检查另行说明。

初始化完成后，项目 README、AGENTS、raw 与 wiki 的规范 README，以及 Skill 本体和镜像保持固定。日常内容任务维护来源、知识、附件、INDEX 和 SELF 的实际状态，不自动修改用途、范围或流程；query 只读绑定的 wiki，每次仅新增 query-feedback 日志。反馈记录不授权自动优化知识、规范或 Skill，知识更新和工具升级也不自动覆盖已定制入口。只有用户明确要求调整对应说明或约定时，才在该范围内重新定制。

Skill 的创建和修改由本项目 [skill-creator](../skill-creator/SKILL.md) 指导。日常资料入库、查询和审核按实际任务与可用能力执行；预留的 Skill 不作为已经可调用的能力。

保留目标已有内容和 Git 配置。用户要求配置或发布自己的仓库时，按该项明确请求处理。

## 3. 输入设计

结合对话和目标目录取得：目标位置、用户的用途与主题、内容范围、希望如何使用知识，以及已有资料与文件。能从现有内容判断的信息先读取，不重复要求用户描述。

用户在模板副本中要求初始化当前 Wiki 时，该副本就是目标。要求创建到其他位置时，需要在写入前明确目标目录。仅讨论或模拟时，可以暂不确定实际路径。没有初始资料时仍可初始化结构与约定。

结合读者基础、代表性问题及预期结果判断知识需要解释到什么程度。资料类型、关注问题和维护偏好按实际需要补充；由 Agent 归纳已有信息并提出建议，不要求用户填写固定问卷。

在工作方式中一并确认该 Wiki 的标识、query 名称、本体目录和实际共享技能目录。名称为 `query-<wiki-id>`，例如 `query-quant-wiki`，与本体及镜像文件夹名匹配；例子不表示要初始化 QuantWiki。定制文件绑定 Wiki 绝对根目录、其 `wiki/` 与 `query-feedback/`。Codex 用户级共享入口为 `~/.agents/skills`，安装仍使用本次实际确认的目录，不猜测其他环境。仅修改模板不构成向用户共享目录或其他项目安装的授权。

## 4. 原则设计

1. **合并相关问题，按需澄清。** 允许用户从不完整的想法开始。先给例子、推荐方案和选项，将可一起回答的问题放在同一轮；只追问影响方案的缺口，不为字段或流程环节分别增加确认。需求足以支撑方案时结束澄清，不以固定轮数判断完成。
2. **按依赖组织方案，尽早验证。** 用途与边界决定来源、目录、页面及检查要求。相关环节可以同轮推荐和讨论；尽早用真实材料检验页面，不等所有规则都讨论完。
3. **按已有信息推进。** 已明确的需求和有效授权直接使用；方案明确后连续完成范围内的定制与核对。
4. **分开显示讨论与建库进度。** 从首轮起分别说明需求讨论和实际建库的状态，百分比依据各自的明确事项或实际产物估算。讨论结束不表示文件已落实；实际建库完成验收交付后才显示 100%。
5. **保护和复用现有内容。** 修改前读取已有文件，只调整当前方案影响的内容；不改写原始证据，不为分类完整而建立空目录。
6. **状态与实际内容一致。** 区分已保存资料、已形成知识、计划内容与未核验结论；导航指向实际文件。
7. **按项目明确证据边界。** 在设计页面前判断该用途需要什么依据、如何区分来源陈述与新增判断。只澄清影响结果且尚未明确的部分，不把某个专业项目的限制变成所有 Wiki 的固定问卷。

## 5. 工作流程设计

按以下依赖组织工作：**用途与边界 → raw 来源与保存形式 → 整体文件夹与页面设计 → 检查与工作约定 → 定制文件 → 核对与交付**。这不是一环节一轮对话的要求。来源与保存、目录与页面样例、检查与写回方式可以分别合并讨论；已有结论直接复用，新回答改变前提时只修正受影响部分。

分别展示需求讨论和实际建库，不合成一个总百分比：

| 进度 | 判断依据 | 完成条件 |
| --- | --- | --- |
| 需求讨论 | 已明确的用途、相关边界、来源、组织、页面设计与工作方式。 | 重要未决问题已解决，本轮方案与交付范围足以指导工作，显示“已完成”。 |
| 实际建库 | 文件尚未写入时显示“未开始”；开始后依据约定文件、内容及核对结果估算。 | 七项通用指标均有达标依据，本轮交付完成，才显示 100%。 |

两个进度分别以 5 个百分点为粒度粗估，未完成时标注“约”，不表示耗时或知识覆盖率。没有新增结论或产物时保持不变，不按轮次递增；范围变化或发现缺口时可以回退，并说明原因。

首轮和每轮澄清、方案讨论的回复开头显示简短进度，实施时在关键进展处更新。例如：

```text
需求讨论：约 60%｜实际建库：未开始｜当前：页面设计
本轮待确定：这份真实材料整理出的样稿是否易懂、是否有用。

需求讨论：已完成｜实际建库：约 50%｜当前：定制文件
剩余工作：补齐约定文件，再核对链接与验收条件。
```

示例只展示格式，数值与事项按实际情况填写。模拟时标明“初始化模拟”，实际建库保持“未开始”；需求讨论已充分时可以单独结束，不必模拟写文件和验收。仅停止模拟但仍有缺口时保留讨论进度并列出未决项。无需另建进度或评估文件。

### 5.1 读取现状，明确意图

读取目标中已有的项目说明、SELF、工作约定及与初始化有关的文件。只补读有助于当前判断的资料。目标已初始化时，先核对用户是否明确要求调整约定；普通入库、查询或维护沿用既定流程，发现约定缺口时说明问题与建议，不自动进入定制。

主题与用途、使用者与基础、内容边界、资料来源是 Agent 内部需要弄清的范围，不要求用户填写整套问卷。每轮将可一起回答的相关问题合并；只有后一个问题依赖前一个尚未明确的答案，或合并后难以理解时才拆开。也可给出一组完整建议，请用户只调整不合适的部分。

有真实取舍时，每题给出 2–4 个简短选项，说明单选或可多选，标出有依据的推荐及理由。允许用户组合、修改、自由补充或表示不确定；名称、路径等不硬凑选项。已明确的答案直接使用，普通实现细节自主决定，不追加“是否继续下一步”之类的确认。

先整理已有信息，从容易回答的实际任务开始。例如，用户只说要建 Wiki，可以问：

> 你希望这个 Wiki 最先帮你完成哪类事情？可以多选或补充。
>
> - A. 系统学习一个主题，弄懂概念与联系。
> - B. 分析、评价或比较具体对象，形成有依据的判断。
> - C. 为项目或创作积累可复用的知识。

随后反复执行以下流程，下一轮问题根据实际回答调整：

1. **更新理解。** 区分用户已经说明的需求、Agent 的初步推测和仍未明确的内容；新回答改变原判断时及时修正。
2. **找到并合并关键缺口。** 只询问会改变目标、质量、范围、成本或工作方式的问题，将可一起决定的事项合并。用户只回答部分时，仅补问仍影响方案的未答项，不把未答项视为已确认。
3. **帮助表达，再追问。** 用户回答笼统、说“不知道”或“都行”时，给出具体使用场景、可选方向和推荐理由，让用户选择、修正或补充。比如只说“想学习”，可用“看懂基础概念、比较两种方法、完成一个小项目”等具体结果帮助判断，再用选项追问相关基础与限制。
4. **核对变化并收敛。** 简述本轮新增结论及剩余关键问题，用具体场景或样稿核对理解。方案足够明确时汇总并推进，不在每轮重述全部约定；举例或猜测不能当作用户已确认的需求。

“不知道”或“都行”本身不足以说明需求已经清楚。用户明确把某项选择交给 Agent 时，Agent 说明推荐理由并在该范围内推进，保留其他尚未解决的关键问题。

围绕主要任务确认核心范围、相关主题的涉及程度和范围外内容，结合读者基础与代表性问题确定需要解释到什么程度。

例如，研究类 Wiki 可以围绕“比较两种方法在某个任务下为何表现不同”确定范围与深度。保留比较对象、适用条件和实际依据，区分作者报告、整理者解释与实际验证；说明已有判断，以及什么新证据可能改变它。只澄清仍会影响判断的缺口。这个案例用于帮助表达研究用途，需求已经清楚时直接沿用；其他 Wiki 按自身用途确定要求。

在提出具体页面样例前，判断当前用途是否还需要明确证据边界。例如，评价类项目可能需要区分作者观点、用户感受和 AI 推断；实验类项目可能需要区分文献结论与实际验证。先结合已有资料和约定给出建议，只询问会影响页面可信度的缺口，并可与用途、来源一起确认。普通资料整理已有引用规则时直接沿用；评分、AI 分析等是否适用由具体项目决定，不预设所有 Wiki 都禁止评分或 AI 分析。

本阶段结束时，应能依据已有信息及用户认可的具体场景，说明主要用途、使用者与基础、初步内容和证据边界及来源情况；暂时没有资料也可作为明确现状。正式创建还需明确目标位置，模拟可保留待定。信息足以支撑方案时直接推进，保存形式、目录和检查项可按依赖合并讨论。

目标位置或会明显影响用途与范围的重要问题尚未明确时，继续讨论可判断的部分，先解决缺口再写入受影响的定制内容。

### 5.2 提出并确定方案

Agent 给出简短的推荐方案，说明用途与范围、来源和知识的组织方式、必要的工作约定、本次会完成哪些内容，以及是否处理初始资料。

解释推荐的理由及重要取舍，根据用户反馈修正。用户已经明确选择时按其选择推进；普通命名、文件组织和链接细节自主处理。

在用途与边界清楚后，按以下依赖形成方案，沿用第 5.1 节的合并提问方式。先给完整推荐，让用户调整有分歧的部分；不要把下列事项机械拆成独立轮次：

1. **raw 来源与保存。** 将资料渠道、类型和保存形式作为一组方案推荐，复用已明确的分工。分工尚不清楚时，给出用户提供、AI 检索或两者结合等选项；按主题推荐文章、论文、书籍、音视频或代码等类型。需要 AI 补充时，检索具体网站、教材、课程或作者资料，给出少量候选及理由；不以“没有现成资料”结束来源讨论。

   针对选定类型给出具体保存建议。例如，网页或 PDF 保存实际取得的副本并转成忠实的 Markdown；音视频保存实际取得的原文件，并根据内容与能力确定字幕、转写等转录形式。说明实际能取得和转录的范围，取得受限或无法完整转录时交代缺失，不把链接或摘要当作完整原件与转录。每条仍只保留原件、`article.md` 和 `README.md`，按入库日期保存到 `raw/YYYY-MM-DD/条目名称/`。用一个示例条目让用户确认保存方式，并确定 AI 检索补充的范围。

   用途和来源方向初步明确后，就选一份实际可读取的材料：优先复用用户资料，没有时按已明确的检索范围查找。读取相关正文，保留来源定位，用同一材料准备保存示例和页面短样稿，不等目录、检查项与工作方式全部定稿。材料不可得时说明限制，先推进可确定的结构与约定。
2. **整体文件夹设计。** 根据用途和资料形式复用已读材料，必要时补充检索并优先读取原始来源或官方资料；提出覆盖目标根目录、`raw/`、`wiki/`、仅存查询日志的 `query-feedback/` 和实际使用的 Skill 入口的简短目录树，另说明共享镜像的确认位置。说明项目 README、AGENTS、SELF、INDEX 及各内容目录的职责，区分模板已有结构与建议新增部分。给出推荐理由，请用户对分类、命名和查找方式提出建议；有重要取舍时提供少量可选设计。没有检索到可用材料时如实说明，区分已有依据与建议。
3. **Wiki 页面内容与关系。** 将目录草案与一份真实材料的短样稿一起展示，标出来源、依据位置及整理者的解释，让用户判断是否看得懂、是否解决实际问题。根据反馈一起调整页面写法、深度与目录；其余页面按需要补充提纲和关联，不为凑数量逐页提问。

   样稿默认在对话中展示，讨论或模拟本身不授权入库。正式保存按本轮已明确的写入范围执行，只有实际正文才能加入导航。找不到可用材料时，可用明确标注的构造示例演示格式，但不能伪造来源或把它当成真实材料验证；保留未验证项。
4. **检查约定。** 根据已确认的 raw、Wiki 规范推荐具体检查项。raw 只查保存位置、三部分齐全且可读、来源说明清楚；Wiki 覆盖内容质量、依据与引用、链接与导航、目录组织、一致性与更新、当前状态与知识缺口。确定工具和 AI 分工，区分确定问题与待核疑点；不默认逐段校对转录。
5. **工作方式与交付。** 根据已明确的用途、来源和页面设计，确定具体入库做法，以及查询、审核的输入和输出。查询只读绑定的 wiki、不读 raw，每次仅新建反馈日志；需要修改知识时作为另外的内容任务处理。合并确认 query 名称、本体目录、Wiki 绝对根目录与共享安装目录，复用已有答案，不按字段逐次提问。明确本轮是否处理初始资料、镜像安装与独立目录查询的验收要求及下一步。

复用早期真实样稿检验预期结果，按需要补充范围内、范围外及边界案例。没有可用材料时可用已标明性质的构造案例推演规则，仍可完成结构与约定的初始化，真实材料处理保留未验证。重要歧义带回讨论，边界需要扩展时说明影响并按用户选择调整。

本阶段完成时，用途、边界、组织方式、知识要求和操作约定应足以指导定制与后续工作。七项通用指标见第 6 节，按用途补充知识质量要求。需求讨论可标为“已完成”；已授权创建时进入定制，仅讨论或模拟时交付方案与未验证项即可。

### 5.3 定制目标文件

在已确定的方案内完成定制。新目录带入所需的模板管理文件、本 Skill、wiki-ingest 与 wiki-query 的设计和执行文件，以及其他实际启用的 Skill 和其依赖；不复制 `.git/`。已有 Wiki 保留有效内容，补齐缺失文件并调整受方案影响的说明与约定。

各文件的职责与定制要求：

- [项目 README](../../../README.md)：说明用户自己的 Wiki 及使用入口。
- [AGENTS](../../../AGENTS.md)：指向目标实际存在的规范与可用 Skill，落实操作及写回约定。
- [来源规则](../../../raw/README.md)：记录已确认的来源渠道与类型、原件与转录形式、按入库日期保存的三部分结构、来源说明和基础检查要求。
- [知识页面规范](../../../wiki/README.md)：记录已确认的目录与页面职责、页面写法与关系、读者基础、解释深度，以及证据、维护和检查要求。
- [SELF](../../../wiki/SELF.md)：记录服务对象、用途、内容边界、实际已有内容、缺口与下一步。
- [INDEX](../../../wiki/INDEX.md)：连接实际存在的管理入口和知识页面。
- [wiki-ingest 说明](../wiki-ingest/README.md)与 [Skill](../wiki-ingest/SKILL.md)：在目标 Wiki 中保留“看 Wiki 的目的 → 围绕目的读材料 → 整合进 Wiki → 检查并交付”四步框架，将整理重点与深度、来源处理、页面落点、检查及写回方式落实到对应步骤。共用规则引用目标的 raw 和 Wiki 规范。
- [wiki-query 说明](../wiki-query/README.md)与 [Skill](../wiki-query/SKILL.md)：模板保留通用入口，目标 Wiki 中改为已确认的 `query-<wiki-id>`，description 说明该 Wiki 的主题、用途与查询触发条件。本体存于目标技能目录，README、SKILL 与必要随包材料自包含绑定 Wiki 绝对根目录、`<ROOT>/wiki` 和 `<ROOT>/query-feedback`；定制阶段创建这个反馈目录，只供后续查询新增日志，不放占位 README 或预先编造日志。不依赖启动 cwd、临时对话或兄弟 Skill。目标 AGENTS、README 及其他入口使用实际名称和路径，不留下指向已改名模板目录的链接。

在目标 AGENTS 和定制后的 ingest 中落实初始化后的写入边界：介绍与规范文件固定，来源条目 README 仍可按既定规则记录出处，INDEX 维护实际导航，SELF 更新覆盖、缺口与下一步，用途和范围不随日常任务改变。后续调整约定以用户明确要求的范围为准。

模板其他管理文件按实际需要保留。携带预留设计时明确其状态，不把它列为可执行 Skill。全部链接按目标中的实际文件核对。

上述文件定制完成时，已确定的约定应落实到目标文件，README 已适应该用户，SELF 和导航反映实际内容；本体就绪不等于共享镜像已安装或查询已验收。

#### query 镜像安装

定制本体后，将其 README、SKILL 与必要随包材料复制为已确认共享目录中的同名镜像，不以只复制入口或链接到本体代替完整交付。逐一核对相对文件清单和内容哈希一致。

- 同名且清单、内容相同：幂等跳过复制，再核对实际绑定与可用状态。
- 同名但内容不同：保留现有用户技能，说明冲突路径及差异，只暂停镜像安装部分，继续本体与其他不受影响工作。不得覆盖旧 Wiki 的技能或宣称新入口已对外安装。
- 安装受限：报告具体权限或环境限制、本体已完成部分与镜像未完成部分，不把本地文件写入成功当作共享安装成功。

安装属于已明确的初始化范围，不默认在以后知识更新时重新定制或升级镜像。用户只要求修改模板时，以临时 Wiki 和临时共享目录验证这些规则，不写用户全局目录或其他项目。

### 5.4 核对并交付

依据第 6 节的七项通用指标及本轮知识质量要求检查目标文件。对照方案核对 raw 来源与保存方式、Wiki 目录和页面职责、检查项是否已写入，检查文件与链接，并用代表性任务和边界案例检验规则能否指导判断。原有资料、知识和 Git 配置得到保留。

query 镜像安装后，从 Wiki 外的独立工作目录使用镜像入口完成一次代表性查询。记录实际文件读取和搜索的路径与范围，核对查询只读取绑定的 wiki、未读取或枚举 raw 及越界目标；另比较查询前后的文件清单与哈希，确认唯一新增文件为绑定 query-feedback 目录中的查询日志，其余 Wiki 文件、说明与规范、query 本体和镜像均未改变，本体与镜像内容仍一致。文件哈希不用于证明读取边界。反馈目录只存日志，不因反馈产生自动优化写入。目录外运行未完成或镜像受限、冲突时，分别报告未验证或未完成项，不能宣布共享安装和独立使用已验收。

逐项交付结论、可定位的依据、缺口及下一步。文件检查、场景推演与真实运行分别说明；未做达标所需检查时标记“未验证”。

发现缺口时返回相应阶段：定位与边界问题继续讨论，约定遗漏或链接错误在范围内修正，需要改变用途或范围时与用户商量。七项指标均有达标依据后，才能宣布本轮初始化完成。知识建设的后续待办可以保留，现有知识质量及实际运行结果按检查范围另行说明。

交付目标位置、入口、主要定制结果和逐项评估，说明 query 实际名称、绝对绑定、本体与共享镜像位置、哈希核对及目录外查询结果；区分本体就绪、镜像安装与实际查询验收。说明哪些文件已固定、哪些内容可日常维护，依据实际完成情况更新进度。

## 6. 输出设计

每轮先分开显示需求讨论与实际建库的进度，再说明本轮新增结论、当前环节和待解决的问题。有真实取舍时合并给出选项与推荐理由；信息充分时直接推进，不为延续对话追加问题。来源与保存建议、目录草案和真实页面样稿按依赖组合展示，尽早接收反馈，再确定检查与工作约定。实施后交付定制后的 Wiki、目标位置、使用入口及逐项评估；模拟结束交付已定约定与未验证项。

### 6.1 评估指标与验收条件

评估分两层：七项通用指标检查初始化是否完成；按用途确定的知识质量要求指导后续内容建设，并检查这些要求是否已落实。

| 指标 | 达标条件 | 判断依据 |
| --- | --- | --- |
| 用途可执行 | 明确服务对象、主要任务与预期结果，能用用户认可的具体场景说明怎样的知识或回答对用户有用。 | 定位说明、澄清结论及代表性问题的预期结果。 |
| 范围可判定 | 明确核心范围、相关主题的涉及程度及当前范围之外的内容，能够处理边界案例。 | 已保存的边界约定及范围内、范围外、边界案例的判断理由。 |
| 深度有依据 | 明确读者基础和主要页面需要解释的内容、深度，要求能够支撑实际用途。 | 知识页面规范及代表性任务对解释要求的检验。 |
| 证据规则可执行 | 来源保存、引用与追溯方式明确，能按项目要求区分来源陈述、观点、推断与实际核验。 | 已保存的项目约定及真实材料样稿；无可用材料时采用明确标注的规则推演。 |
| 操作约定可执行 | 目标 ingest 与 query 已按用途定制；query 名称、绝对绑定、只读知识与反馈日志边界明确，共享镜像能从 Wiki 外独立使用；审核方式明确。 | 定制后的文件、镜像位置与同内容哈希、目录外代表查询及前后文件对照；可用与预留能力状态准确。 |
| 文件落实一致 | 文件与导航落实已确定方案，入口使用实际 query 名称，镜像材料齐全且同内容，引用有效，原有内容及 Git 配置得到保留。 | 目标文件、共享镜像、链接检查、清单哈希及修改前后的对照。 |
| 后续工作可接续 | 当前内容、缺口与下一步准确，后续 Agent 仅依据保存文件即可说明下一项任务、输入、预期产物及固定文件与日常维护内容的边界。 | SELF、使用入口、AGENTS 与定制后的 ingest。 |

知识质量要求按用途确定。例如，方法比较需要明确比较维度、适用条件和证据要求；操作实践需要明确前置条件、步骤及结果检查。初始化时保存这些要求，已有知识页面是否达到要求按实际核验另行说明。

### 6.2 评估结果与完成标准

每项评估给出结论、依据、缺口及下一步。结论采用：

- **达标**：满足验收条件，有可定位的文件或检查证据。
- **待补齐**：约定缺失或不完整，尚不足以指导工作。
- **未验证**：相关约定已形成，达标所需检查尚未完成。

七项通用指标均有达标依据，影响用途、范围、知识要求和操作方式的关键缺口已解决，且本轮约定的交付已完成，才能宣布本轮初始化完成。没有资料时可通过构造案例推演规则，完成结构与约定的验收；知识覆盖、内容质量和实际运行结果单独说明。

## 8. 校验设计

静态检查设计与实现是否一致、必需方法是否转化为具体动作、七项评估及阶段完成条件是否落实、文件引用是否可定位，以及输出是否如实区分初始化与知识建设。

按修改范围选取需求模糊、需求已明确、没有资料、已有 Wiki、新目标目录或仅讨论的场景。检查来源建议、目录与页面、检查及工作约定是否按依赖组合，是否复用已有结论和授权，以及计划、实际文件和导航是否分明。

重点核对以下变更场景：

- **合并提问**：相关问题能同轮回答，用户只回答部分时只追问关键未答项；不因流程分节增加轮次。
- **按需澄清**：需求笼统时提供例子和建议，已明确或已授权代选时直接推进；不把推测当确认。
- **项目差异**：需要专业判断的项目在样稿前明确关键依据；普通资料整理不额外套用专业证据问卷。
- **真实材料**：尽早读取一份材料展示短样稿，依据和解释可分辨；不可得时如实标记，构造示例不算真实验证。
- **入库定制**：有无初始资料都检查目标 ingest 的说明与 Skill 是否落实项目约定；用代表性材料核对选材、深度和页面落点，流程定制与实际入库分别说明。
- **query 定制与安装**：本体和镜像名称、绝对绑定及随包材料一致；同内容重复安装可跳过，异内容冲突不覆盖；安装受限不宣称已对外安装。模板修改只用临时目标验证，不安装到用户全局目录。
- **目录外查询**：从独立 cwd 使用镜像读取实际 wiki，raw 未读，仅新增一份反馈日志，其他文件与本体、镜像哈希不变；静态检查和规则推演不能代替这项实际查询。
- **固定边界**：日常新增来源、维护 INDEX 与 SELF 的实际状态不改写介绍与规范；缺约定不自动进入定制；用户明确要求调整时只修改对应范围，本次条目决定不自动成为长期约定。
- **进度与模拟**：讨论与建库分别反映实际成果，不按轮次递增；讨论结束时建库仍可未开始，实际验收前不能显示建库 100%，模拟不产生未经授权的写入。

文档检查和场景推演分别说明；只有完成实际初始化并检查产物，才能报告真实运行结果。不要求默认建立测试目录或评分器。
