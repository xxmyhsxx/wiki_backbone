# Wiki Init

状态：设计已确认，执行规范已按本设计同步。初始化流程由 [SKILL.md](SKILL.md) 执行。

## 1. 任务与设计目标

基于通用 LLM Wiki 模板，主动引导用户明确用途、范围和组织方式，完成用户自己的 Wiki 初始化。交付后，用户和新进入的 Agent 能从文件中理解 Wiki 的目的、内容边界、知识质量要求、当前内容、工作方式和下一步。初始化依据明确的评估指标验收，结论附有可定位的依据。

关键问题及处理方法：

| 关键问题 | 为什么影响结果 | 方法与质量依据 |
| --- | --- | --- |
| 用户需求不完整或难以表达 | 只知道主题，仍不足以判断用途、边界和组织方式。 | 主动多轮澄清；优先用选择题，给出例子、推荐理由，再按回答追问并核对理解。 |
| 用户不清楚原始材料如何积累 | 只问有没有资料，无法确定后续取得和保存方式。 | 主动推荐资料来源、材料类型及原件、转录的保存形式，再请用户选择或调整。 |
| 用户需要帮助判断组织方式 | 直接要求用户给目录，会把设计工作交回用户。 | Agent 先推荐整体文件夹设计，再给出具体页面提纲或短样例，让用户据此提出建议。 |
| 用户难以判断初始化进展 | 讨论与文件定制可能跨多轮对话。 | 从首轮起展示百分比、当前环节和下一步，按明确的阶段与实际成果估算。 |
| 模板没有充分个性化 | 文件存在仍可能保留无关的模板说明或错误描述。 | README、SELF、工作约定和导航共同反映用户已确定的方案及实际内容。 |
| 范围与深度难以判断 | 主题名称不足以判断材料是否收录、页面需要解释到什么程度。 | 用代表性任务和范围内、范围外、边界案例检验约定，解决会改变判断的歧义。 |
| 完成标准不够具体 | 文件已写入时，关键问题仍可能未解决。 | 提前明确验收要求，按七项通用指标检查，交付结论、依据、缺口及下一步。 |

## 2. 使用边界

用户要求创建或初始化 Wiki、在模板副本中定制自己的 Wiki，或补全已有 Wiki 的初始化约定时使用。

本 Skill 负责意图澄清、方案确定、文件定制和核对，并帮助用户确定知识质量要求。已有知识的覆盖、质量及实际运行结果按实际检查另行说明。是否同时处理初始资料，作为本次方案的一部分明确；已有资料可以用于判断组织方式，资料保存与知识建设分别说明。

Skill 的创建和修改由本项目 [skill-creator](../skill-creator/SKILL.md) 指导。日常资料入库、查询和审核按实际任务与可用能力执行；预留的 Skill 不作为已经可调用的能力。

保留目标已有内容和 Git 配置。用户要求配置或发布自己的仓库时，按该项明确请求处理。

## 3. 输入设计

结合对话和目标目录取得：目标位置、用户的用途与主题、内容范围、希望如何使用知识，以及已有资料与文件。能从现有内容判断的信息先读取，不重复要求用户描述。

用户在模板副本中要求初始化当前 Wiki 时，该副本就是目标。要求创建到其他位置时，需要明确目标目录。没有初始资料时仍可初始化结构与约定。

结合读者基础、代表性问题及预期结果判断知识需要解释到什么程度。资料类型、关注问题和维护偏好按实际需要补充；由 Agent 归纳已有信息并提出建议，不要求用户填写固定问卷。

## 4. 原则设计

1. **主动多轮澄清需求。** 允许用户从不完整、笼统的想法开始。Agent 负责发现缺口，优先用选择题，提供例子与建议、继续追问并修正理解；每轮聚焦一小组关键问题，已明确的信息直接复用。结束澄清以需求能支撑具体方案为准，不以问过一轮或达到固定轮数为准。
2. **按顺序主动推荐。** 先讨论用途与边界，再依次确定原始材料来源与保存形式、整体文件夹设计、Wiki 页面、检查与工作约定。Agent 检索相关材料，给出具体设计、推荐理由和重要取舍，请用户选择、修改或补充。
3. **按已有信息推进。** 已明确的需求和有效授权直接使用；方案明确后连续完成范围内的定制与核对。
4. **展示有依据的百分比进度。** 从首轮起，每轮澄清与方案讨论都显示百分比和当前环节；实施时在关键进展处更新。进度依据已明确事项和实际产物估算，达到阶段完成条件后才能进入下一区间，验收交付完成才显示 100%。
5. **保护和复用现有内容。** 修改前读取已有文件，只调整当前方案影响的内容；不改写原始证据，不为分类完整而建立空目录。
6. **状态与实际内容一致。** 区分已保存资料、已形成知识、计划内容与未核验结论；导航指向实际文件。

## 5. 工作流程设计

讨论顺序为：**用途与边界 → raw 来源与保存形式 → 整体文件夹设计 → Wiki 页面内容与关系 → 检查与工作约定 → 定制文件 → 核对与交付**。每个环节先由 Agent 给出推荐，再讨论用户的选择与建议。当前环节的重要问题明确后进入下一环节；已有结论直接复用，新回答影响先前决定时返回相应环节修正。

百分比按以下四个阶段估算，用于说明本轮初始化进展，不表示耗时比例或知识覆盖率：

| 阶段 | 进度区间 | 进入下一区间的条件 |
| --- | --- | --- |
| 明确用途与边界 | 0–25% | 用途、读者基础、初步边界、来源现状和目标位置已清楚。 |
| 确定组织与工作方案 | 25–50% | raw 来源与保存形式、整体文件夹、页面设计、检查与工作约定已确定。 |
| 定制文件 | 50–75% | 已确认方案及本轮约定的内容已落实到目标文件。 |
| 核对与交付 | 75–100% | 七项通用指标均有达标依据，本轮交付完成。 |

区间内根据已明确事项或实际产物，以 5 个百分点为粒度估算，未完成时标注“约”。没有新增结论或产物时进度保持不变；范围调整或发现缺口时可以回退，并解释原因。各阶段占比是统一的展示约定。

首轮和每轮澄清、方案讨论的回复开头显示简短进度，实施时在关键进展处更新。例如：

```text
Wiki 初始化：约 20%｜当前：明确用途与边界
已明确：用途、读者基础、资料来源分工。
下一步：确定内容边界，再讨论原件与转录的保存形式。
```

示例仅展示格式，数值与事项按实际情况填写。仅讨论或模拟时标明范围，不因对话结束而显示 100%。无需额外建立进度或评估文件。

### 5.1 读取现状，明确意图

读取目标中已有的项目说明、SELF、工作约定及与初始化有关的文件。只补读有助于当前判断的资料。

主题与用途、使用者与基础、内容边界、资料来源是 Agent 内部需要弄清的范围，不要求用户一次说全。每轮优先问一两个相关问题，每题给出 2–4 个简短选项，说明是单选还是可多选；有推荐依据时标出推荐项并简述理由。允许用户组合、修改或自由补充，也可以表示不确定；名称、路径等具体信息可直接提问，不硬凑选项。

先整理已有信息，从容易回答的实际任务开始。例如，用户只说要建 Wiki，可以问：

> 你希望这个 Wiki 最先帮你完成哪类事情？可以多选或补充。
>
> - A. 系统学习一个主题，弄懂概念与联系。
> - B. 分析、评价或比较具体对象，形成有依据的判断。
> - C. 为项目或创作积累可复用的知识。

随后反复执行以下流程，下一轮问题根据实际回答调整：

1. **更新理解。** 区分用户已经说明的需求、Agent 的初步推测和仍未明确的内容；新回答改变原判断时及时修正。
2. **找到关键缺口。** 选择最影响用途、边界或方案的一小组问题继续讨论，已清楚的事项不重复询问。
3. **帮助表达，再追问。** 用户回答笼统、说“不知道”或“都行”时，给出具体使用场景、可选方向和推荐理由，让用户选择、修正或补充。比如只说“想学习”，可用“看懂基础概念、比较两种方法、完成一个小项目”等具体结果帮助判断，再用选项追问相关基础与限制。
4. **复述并核对。** 用简短的话复述当前理解，通过一个具体使用场景核对目标与预期结果。仍有重要偏差或缺口时继续下一轮，不能将 Agent 的举例或猜测当作用户已经确认的需求。

“不知道”或“都行”本身不足以说明需求已经清楚。用户明确把某项选择交给 Agent 时，Agent 说明推荐理由并在该范围内推进，保留其他尚未解决的关键问题。

围绕主要任务确认核心范围、相关主题的涉及程度和范围外内容，结合读者基础与代表性问题确定需要解释到什么程度。

本阶段结束时，应能依据已有信息及用户认可的具体场景，说明目标位置、主要用途、使用者与基础、初步内容边界和来源情况；暂时没有资料也可作为明确现状。影响定位的重要缺口解决后进入方案设计，保存形式、目录和检查项在下一阶段继续用同样的方式讨论。已有信息充分时直接推进，无需为了多轮而增加提问。

目标位置或会明显影响用途与范围的重要问题尚未明确时，继续讨论可判断的部分，先解决缺口再写入受影响的定制内容。

### 5.2 提出并确定方案

Agent 给出简短的推荐方案，说明用途与范围、来源和知识的组织方式、必要的工作约定、本次会完成哪些内容，以及是否处理初始资料。

解释推荐的理由及重要取舍，根据用户反馈修正。用户已经明确选择时按其选择推进；普通命名、文件组织和链接细节自主处理。

在用途与边界清楚后，按以下顺序逐项形成方案，沿用第 5.1 节的选择题与多轮澄清方式。每个环节的后续问题随回答调整，用户难以判断时先给例子和建议；已有结论直接复用：

1. **raw 来源与保存。** 主动讨论三个问题：资料从哪里取得、可能是什么类型、如何保存。先明确由用户提供文件或链接、AI 检索，或两者结合；再根据主题推荐文章、论文、书籍、视频、音频或代码等类型。需要 AI 补充时，检索并推荐具体网站、教材、课程或作者资料等来源。用户不清楚时，Agent 给出少量适合当前用途的候选与推荐理由，再让用户选择；不能仅问“有没有现成资料”就结束这一环节。

   针对选定类型给出具体保存建议。例如，网页或 PDF 保存实际取得的副本并转成忠实的 Markdown；音视频保存实际取得的原文件，并根据内容与能力确定字幕、转写等转录形式。说明实际能取得和转录的范围，取得受限或无法完整转录时交代缺失，不把链接或摘要当作完整原件与转录。每条仍只保留原件、`article.md` 和 `README.md`，按入库日期保存到 `raw/YYYY-MM-DD/条目名称/`。用一个示例条目让用户确认保存方式，并确定 AI 检索补充的范围。
2. **整体文件夹设计。** 根据已确定用途和资料形式，检索相关材料，优先读取原始来源或官方资料；提出覆盖目标根目录、`raw/`、`wiki/` 和实际使用的 Skill 入口的简短目录树。说明项目 README、AGENTS、SELF、INDEX 及各内容目录的职责，区分模板已有结构与建议新增部分。给出推荐理由，请用户对分类、命名和查找方式提出建议；有重要取舍时提供少量可选设计。没有检索到可用材料时如实说明，区分已有依据与建议。
3. **Wiki 页面内容与关系。** 目录方向确定后，推荐候选页面，并选 2–3 个代表性页面给出简短提纲或正文样例。说明每页解决什么问题、解释到什么程度、如何使用例子与来源，以及从哪些入口进入、与哪些页面关联。请用户选择或调整页面写法，不能只确认目录名称。候选页面作为计划，只有实际正文才能加入导航。
4. **检查约定。** 根据已确认的 raw、Wiki 规范推荐具体检查项。raw 只查保存位置、三部分齐全且可读、来源说明清楚；Wiki 覆盖内容质量、依据与引用、链接与导航、目录组织、一致性与更新、当前状态与知识缺口。确定工具和 AI 分工，区分确定问题与待核疑点；不默认逐段校对转录。
5. **工作方式与交付。** 确定入库、查询、审核的输入、输出和写回方式，以及本轮是否处理初始资料、验收要求和下一步。

用代表性任务检验预期结果，用范围内、范围外及边界案例检验收录与解释要求。优先复用用户的问题和资料；没有资料时可构造案例，并说明案例及推演的性质。将发现的重要歧义带回讨论，边界需要扩展时说明影响并按用户明确选择调整。

本阶段完成时，用途、边界、组织方式、知识要求和操作约定应足以指导定制与后续工作。七项通用指标见第 6 节，按用途补充知识质量要求；重要未决问题解决后进入定制。

### 5.3 定制目标文件

在已确定的方案内完成定制。新目录带入所需的模板管理文件、本 Skill 的设计与执行文件，以及实际启用的 Skill 和其依赖；不复制 `.git/`。已有 Wiki 保留有效内容，补齐缺失文件并调整受方案影响的说明与约定。

各文件的职责与定制要求：

- [项目 README](../../../README.md)：说明用户自己的 Wiki 及使用入口。
- [AGENTS](../../../AGENTS.md)：指向目标实际存在的规范与可用 Skill，落实操作及写回约定。
- [来源规则](../../../raw/README.md)：记录已确认的来源渠道与类型、原件与转录形式、按入库日期保存的三部分结构、来源说明和基础检查要求。
- [知识页面规范](../../../wiki/README.md)：记录已确认的目录与页面职责、页面写法与关系、读者基础、解释深度，以及证据、维护和检查要求。
- [SELF](../../../wiki/SELF.md)：记录服务对象、用途、内容边界、实际已有内容、缺口与下一步。
- [INDEX](../../../wiki/INDEX.md)：连接实际存在的管理入口和知识页面。

模板其他管理文件按实际需要保留。携带预留设计时明确其状态，不把它列为可执行 Skill。全部链接按目标中的实际文件核对。

本阶段完成时，已确定的约定应落实到目标文件，README 已适应该用户，SELF 和导航反映实际内容。

### 5.4 核对并交付

依据第 6 节的七项通用指标及本轮知识质量要求检查目标文件。对照方案核对 raw 来源与保存方式、Wiki 目录和页面职责、检查项是否已写入，检查文件与链接，并用代表性任务和边界案例检验规则能否指导判断。原有资料、知识和 Git 配置得到保留。

逐项交付结论、可定位的依据、缺口及下一步。文件检查、场景推演与真实运行分别说明；未做达标所需检查时标记“未验证”。

发现缺口时返回相应阶段：定位与边界问题继续讨论，约定遗漏或链接错误在范围内修正，需要改变用途或范围时与用户商量。七项指标均有达标依据后，才能宣布本轮初始化完成。知识建设的后续待办可以保留，现有知识质量及实际运行结果按检查范围另行说明。

交付目标位置、入口、主要定制结果和逐项评估，依据实际完成情况更新进度。

## 6. 输出设计

每轮讨论先显示百分比与当前环节，再简述已确认事项和关键缺口，优先以带例子、推荐理由的选择题推进。按顺序交付来源与保存建议、整体目录树、代表性页面提纲或样例、检查与工作约定，逐步确定本轮验收要求；实施后交付定制后的 Wiki、目标位置、使用入口及逐项评估。

### 6.1 评估指标与验收条件

评估分两层：七项通用指标检查初始化是否完成；按用途确定的知识质量要求指导后续内容建设，并检查这些要求是否已落实。

| 指标 | 达标条件 | 判断依据 |
| --- | --- | --- |
| 用途可执行 | 明确服务对象、主要任务与预期结果，能用用户认可的具体场景说明怎样的知识或回答对用户有用。 | 定位说明、澄清结论及代表性问题的预期结果。 |
| 范围可判定 | 明确核心范围、相关主题的涉及程度及当前范围之外的内容，能够处理边界案例。 | 已保存的边界约定及范围内、范围外、边界案例的判断理由。 |
| 深度有依据 | 明确读者基础和主要页面需要解释的内容、深度，要求能够支撑实际用途。 | 知识页面规范及代表性任务对解释要求的检验。 |
| 证据规则可执行 | 明确来源保存、引用与追溯方式，能够区分来源陈述、整理者解释和实际核验。 | 来源与知识页面规范，以及一份来源或构造案例的处理推演。 |
| 操作约定可执行 | 明确入库、查询、审核等工作的输入、输出、写回方式，可用和预留能力状态准确。 | Agent 约定、实际 Skill 文件及典型任务的处理说明。 |
| 文件落实一致 | 文件与导航落实已确定方案，引用有效，原有内容及 Git 配置得到保留。 | 目标文件、链接检查及修改前后的对照。 |
| 后续工作可接续 | 当前内容、缺口与下一步准确，后续 Agent 仅依据保存文件即可说明下一项任务、输入和预期产物。 | SELF、使用入口及依据文件形成的下一步说明。 |

知识质量要求按用途确定。例如，方法比较需要明确比较维度、适用条件和证据要求；操作实践需要明确前置条件、步骤及结果检查。初始化时保存这些要求，已有知识页面是否达到要求按实际核验另行说明。

### 6.2 评估结果与完成标准

每项评估给出结论、依据、缺口及下一步。结论采用：

- **达标**：满足验收条件，有可定位的文件或检查证据。
- **待补齐**：约定缺失或不完整，尚不足以指导工作。
- **未验证**：相关约定已形成，达标所需检查尚未完成。

七项通用指标均有达标依据，影响用途、范围、知识要求和操作方式的关键缺口已解决，且本轮约定的交付已完成，才能宣布本轮初始化完成。没有资料时可通过构造案例推演规则，完成结构与约定的验收；知识覆盖、内容质量和实际运行结果单独说明。

## 8. 校验设计

静态检查设计与实现是否一致、必需方法是否转化为具体动作、七项评估及阶段完成条件是否落实、文件引用是否可定位，以及输出是否如实区分初始化与知识建设。

按修改范围选取代表性场景检查：需求模糊、需求已明确、没有资料、已有 Wiki、新目标目录或用户只要求讨论。核对是否依次讨论用途与边界、raw、整体文件夹、页面、检查与工作约定；来源不明时是否主动给出渠道、类型与保存形式建议，目录是否有具体推荐，页面是否有提纲或样例，检查项是否来自用户确认的规范。重点观察是否复用已明确信息、是否在授权范围内定制，以及计划页面、实际内容和导航是否分明。边界存在歧义或未做必要检查时，继续处理缺口并如实标记状态。

多轮澄清重点核对四种情况：只给主题时能从实际任务追问；回答“不知道”或“都行”时能给出例子、建议和后续问题；回答改变原判断时能修正理解；需求已充分或某项已明确交给 Agent 决定时，能在已明确范围内推进。示例与推测不能被记成用户结论，重要缺口不能因已问过一轮而被跳过。

同时检查每轮是否有简短百分比进度，是否优先提供可理解、可补充的选项。进度应能对应已明确事项或实际产物；没有新成果时不增加，范围变化时允许解释后回退，仅完成讨论、文件尚未落实或验收仍有缺口时不能显示 100%。

文档检查和场景推演分别说明；只有完成实际初始化并检查产物，才能报告真实运行结果。不要求默认建立测试目录或评分器。
