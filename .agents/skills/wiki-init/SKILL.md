# Wiki Init

## 任务

基于通用模板完成用户自己的 Wiki 初始化：定制 ingest，按用途选择已经实现的对外能力，定制并发布绑定该 Wiki 的完整 use 包，保留轻量 query 兼容。交付目的、内容边界、知识要求、实际内容、工作方式与下一步，依据七项通用指标验收。

本 Skill 的当前设计见 [README](README.md)。执行所需的动作与判断写在本文件中；初始化使用同一项目中的模板管理文件。

## 输入

结合对话和目标目录取得：目标位置、用途与主题、内容范围、希望怎样使用知识，以及已有资料与文件。结合读者基础、代表性问题及预期结果判断解释深度；按需要补充资料类型和维护偏好。

用户在模板副本中要求初始化当前 Wiki 时，以该副本为目标；要求创建到其他位置时，在写入前明确目标目录。仅讨论或模拟时可暂不确定实际路径。能从已有内容判断的信息先读取，不重复询问。没有初始资料时仍可完成结构与约定的初始化。

合并确认 Wiki 标识、对外能力、模式、名称与源目录。完整模式命名 `use-<wiki-id>`，本体与镜像同名，绑定 Wiki 绝对根目录、目标 Wiki 内源包目录和 query-feedback。实际外派需明确接入请求与接收位置，install --project 默认该项目 `.agents/skills/<包名>/`，install --skills-dir 使用确认共享目录；二选一，不能把 `~/.agents/skills` 当项目参数。轻量模式保留 `query-<wiki-id>` 与确认共享目录。仅修改模板不安装全局目录或真实项目。

## 原则

1. **合并相关问题，按需澄清。** 用户可以从不完整的想法开始。先给例子、推荐方案和选项，将可一起回答的问题放在同一轮；只追问影响方案的缺口，不为字段或流程环节分别增加确认。需求足以支撑方案时结束澄清，不按轮数判断完成。
2. **按依赖组织方案，尽早验证。** 用途与边界决定来源、目录、页面及检查要求。相关环节可以同轮推荐和讨论；尽早用真实材料检验页面，不等所有规则都讨论完。普通实现细节自主决定。
3. **复用已明确的信息与授权。** 方案已经明确时继续范围内的定制与核对，不重走已完成的讨论。用户仅要求讨论时交付分析与方案。
4. **只报告有用进展。** 有新增结论、重要进展、方向变化或具体阻塞时说明；区分方案已确定、文件已写入与验证已完成，不要求每轮报告或估算百分比。
5. **保护与复用已有内容。** 修改前读取目标文件，只调整方案影响的内容，保留有效约定、资料、知识和 Git 配置。复制模板管理文件时不复制 `.git/`，不改写原始证据。
6. **范围与内容如实记录。** 计划、已保存资料、已形成知识和实际核验分别说明；导航指向实际文件，知识分类按需要和内容建立。结构初始化、知识质量和实际运行结果分别评估。
7. **按项目明确证据边界。** 在设计页面前判断该用途需要什么依据、如何区分来源陈述与新增判断。只澄清影响结果且尚未明确的部分，不把某个专业项目的限制变成所有 Wiki 的固定问卷。

## 工作步骤

按以下依赖组织工作：**用途与边界 → raw 来源与保存形式 → 整体文件夹与页面设计 → 检查与工作约定 → 定制文件 → 核对与交付**。这不是一环节一轮对话的要求。来源与保存、目录与页面样例、检查与写回方式可以分别合并讨论；复用已有结论，新回答改变前提时只修正受影响部分。

用户询问进度时说明已完成什么、还剩什么。讨论或模拟可单独结束，交付已确定的方案和未决事项，不把方案或模拟当作实际写入和验收；不另建进度文件。

### 1. 读取现状，明确意图

先判断用户要求实际创建、明确补全或调整已有约定，还是仅讨论或模拟。查看目标中已有的项目说明、SELF、Agent 约定、来源和知识页面规范；只补读有助于当前判断的资料。目标已初始化时，普通入库、查询或维护沿用既定流程；缺约定时说明问题与建议，不自动进入定制。用户明确要求调整约定时，只处理对应范围。模拟不要求先确定实际路径，也不自动写入目标文件。

将主题与用途、使用者与基础、内容边界、资料来源作为内部需要弄清的范围，先区分已明确事项、关键缺口和可自主决定的细节。将可一起回答的相关问题合并；只有后一个问题依赖前一个尚未明确的答案，或合并后难以理解时才拆开。也可给出一组完整建议，请用户只调整不合适的部分。

有真实取舍时，每题给 2–4 个简短选项，说明单选或可多选，标出有依据的推荐及理由。允许用户组合、修改、自由补充或表示不确定；名称、路径等不硬凑选项。已明确的答案直接使用，普通实现细节自主决定，不追加“是否继续下一步”之类的确认。

用户只说要建 Wiki 时，从容易回答的实际任务开始。例如：

> 你希望这个 Wiki 最先帮你完成哪类事情？可以多选或补充。
>
> - A. 系统学习一个主题，弄懂概念与联系。
> - B. 分析、评价或比较具体对象，形成有依据的判断。
> - C. 为项目或创作积累可复用的知识。

收到回答后，按下面的过程继续，直到影响定位的关键缺口得到解决：

1. **更新当前理解。** 从回答中提取已说明的目标、背景与限制，区分用户结论、自己的推测和未知信息。回答与原理解不符时先修正判断。
2. **选择并合并关键问题。** 只询问会改变目标、质量、范围、成本或工作方式的问题，将可一起决定的事项合并。用户只回答部分时，仅补问仍影响方案的未答项，不把未答项视为已确认。
3. **先举例、给建议，再追问。** 用户说“不知道”“都行”，或只给出“想学习”等宽泛回答时，提供具体场景或可选方向，并说明自己的推荐理由。例如，用“看懂基础概念、比较两种方法、完成一个小项目”等预期结果帮助用户选择，再用选项追问所选方向需要的基础、资料或限制。让用户选择、纠正或补充，不仅重复原来的抽象问题。
4. **核对变化并收敛。** 简述本轮新增结论及剩余关键问题，用具体场景或样稿核对理解。方案足够明确时汇总并推进，不在每轮重述全部约定；保存形式、目录和检查项也沿用这个过程。

不要替用户补写答案，也不要把自己的例子或建议当作已确认需求。“不知道”或“都行”不足以证明需求已清楚；用户明确将某项选择交给你时，说明推荐理由并在授权范围内推进，其他关键缺口继续澄清。

围绕主要任务确认核心范围、相关主题的涉及程度和范围外内容，结合读者基础与代表性问题确定解释深度。保留来源陈述、整理者解释和实际核验的区别。

研究类 Wiki 可用“比较两种方法在某个任务下为何表现不同”帮助确定范围与深度。结合实际需求保留比较对象、适用条件和依据，区分作者报告、整理者解释与实际验证，说明已有判断及可能改变它的新证据。只追问仍会影响判断的缺口；需求已明确时直接沿用。这个案例只适用于相应研究用途，其他 Wiki 按自己的用途确定要求。

在提出具体页面样例前，检查当前用途是否还有会影响可信度的证据边界未明确。先结合已有资料和约定给出建议，只追问关键缺口，并可与用途、来源一起确认。例如，评价类项目可能要区分作者观点、用户感受与 AI 推断；实验类项目可能要区分文献结论与实际验证。普通资料整理已有引用规则时直接沿用；评分、AI 分析等是否适用由具体项目决定，不预设所有 Wiki 都禁止评分或 AI 分析。

信息足以说明主要用途、使用者与基础、初步内容和证据边界及来源情况时，进入方案设计；暂时没有资料可以作为明确现状。正式创建还需明确目标位置，模拟可保留待定。先解决影响方案的重要缺口再写入受影响的内容，不为凑轮数重复提问。

### 2. 提出并确定方案与验收要求

给出简短的推荐方案，说明用途与范围、来源和知识的组织方式、必要的工作约定、本次会完成哪些内容，以及是否处理初始资料。解释理由和重要取舍，根据用户反馈修正，保留用户明确选择。

在用途与边界清楚后，按以下依赖给出方案，沿用第 1 步的合并提问方式。先给完整推荐，让用户调整有分歧的部分；不要把下列事项机械拆成独立轮次：

1. **确定 raw 来源与保存。** 将资料渠道、类型和保存形式作为一组方案推荐，复用已明确的分工。分工尚不清楚时，给出用户提供、AI 检索或两者结合等选项；按主题推荐文章、论文、书籍、音视频或代码等类型。需要 AI 补充时，检索具体网站、教材、课程或作者资料，给出少量候选及理由；不以“没有现成资料”结束来源讨论。

   为选定类型给出具体保存方案和一个示例条目。网页或 PDF 可保存实际取得的副本，并转成忠实的 Markdown；音视频保存实际取得的原文件，根据内容和现有能力确定字幕、转写等转录形式。说明能取得和转录的范围，受限或缺失部分如实记录，不把链接、摘要说成完整原件与转录。与用户确定方案及 AI 检索补充范围。每条仍只保留原件、`article.md` 和 `README.md`，按入库日期放在 `raw/YYYY-MM-DD/条目名称/`。

   用途和来源方向初步明确后，就选一份实际可读取的材料：优先复用用户资料，没有时按已明确的检索范围查找。读取相关正文及必要图表，记录出处与依据位置，准备保存示例和页面短样稿；不能只凭搜索摘要补出分析。不要等目录、检查项与工作方式全部定稿。材料不可得时说明限制，先推进可确定的结构与约定。
2. **推荐整体文件夹设计。** 根据用途和资料形式复用已读材料，必要时补充检索并优先读取原始来源或官方资料。给出覆盖目标根目录及 `LOG.md`、`raw/`、`wiki/`、仅存查询日志的 `query-feedback/` 和实际使用的 Skill 入口的简短目录树，另说明共享镜像的确认位置；说明项目 README、AGENTS、SELF、INDEX 及各内容目录的职责，区分已有结构与建议新增部分。说明推荐理由，请用户对分类、命名和查找方式提出建议；有重要取舍时提供少量可选设计。没有可用检索结果时说明限制，区分已有依据与建议。
3. **用真实样稿确定页面与目录。** 将目录草案与一份真实材料的短样稿一起展示。先讲对象的作用、整体思路和关键关系，再展开必要细节，说明页面入口与关联；标出来源陈述、整理者解释与待核内容，给出出处和依据位置。请用户判断是否看得懂、是否解决实际问题，根据反馈一起调整深度、写法和目录。其余代表性页面按需要补充提纲，不为凑数量逐页提问。

   样稿默认在对话中展示，讨论或模拟本身不授权入库。正式保存按本轮已明确的写入范围执行，只有实际正文才能加入 INDEX。找不到可用材料时，可用明确标注的构造示例演示格式，但不能伪造来源或把它算作真实材料验证；保留未验证项。
4. **确定检查项。** 根据刚确定的 raw、Wiki 约定推荐具体检查。raw 只查保存位置、三部分齐全且可读、来源说明清楚，不默认逐段校对转录；Wiki 覆盖内容质量、依据与引用、链接与导航、目录组织、一致性与更新、当前状态与知识缺口。说明工具核对结构、AI 阅读并回查来源的分工，与用户确认后保存。
5. **确定工作方式与交付。** 根据用途确定入库做法与对外能力，默认现有 wiki-query；其他能力须实际读取完整规范与依赖，已经实现、适用且经确认才加入。不默认下发 ingest、review、lint、creator，不移植参考项目专用研究或算子能力。合并确认模式、名称、绑定和本轮发布、安装及使用验收范围。query 不读 raw、不改公共知识；包入口统一一次反馈，应用写入由任务与对应能力界定。复用已有结论，不逐字段重复确认。

依据第 4 步的七项通用指标明确本轮验收要求，并按用途补充知识质量要求。复用早期真实样稿检验预期结果，按需要补充范围内、范围外及边界案例。没有可用材料时，可用已标明性质的构造案例推演规则，仍可完成结构与约定的初始化，真实材料处理保留未验证。

发现重要歧义时继续讨论并调整约定。边界需要扩展时，说明对用途、内容和工作方式的影响，按用户明确选择调整。已有资料可用于判断组织方式；是否保存、解读或写成知识页面，按本次明确的需求处理。

用途、边界、组织方式、知识要求和操作约定足以指导工作，且重要未决问题解决后，将需求讨论标为“已完成”。已授权创建时进入定制，仅讨论或模拟时交付方案与未验证项即可。复用已完成阶段，自主处理授权范围内的普通实现细节。

### 3. 定制目标文件

按方案带入所需管理文件、init、ingest 与所选对外模式材料；完整模式复用 wiki-use 入口和工具、现有 query 及确认能力，不复制 .git。已有 Wiki 保留有效内容，只调整受方案影响部分。

轻量模式明确授权更新既有镜像时，修改本体前保存本体和目标镜像原文件清单及内容哈希，核对原安装的已确认版本，留作后续更新依据。完整包复用包工具的发布与安装记录。

不要把模板自带的 `LOG.md` 历史带入目标 Wiki，原地初始化也不将其作为目标记录；保留已有用户记录，不能清空混有用户记录的日志。新目标日志只记录目标自己的实际工作。

结合各文件的职责完成定制：

- [项目 README](../../../README.md)：说明用户自己的 Wiki 和使用入口。
- [AGENTS](../../../AGENTS.md)：引用目标实际存在的规范与 Skill，保留对话、文档和 Skill 的通用表达要求，落实操作及写回约定。
- [raw 规则](../../../raw/README.md)：记录确认的来源渠道与类型、原件与转录形式、入库日期路径、三部分结构、来源说明和基础检查要求。
- [知识页面规范](../../../wiki/README.md)：按用途定制目录、页面职责、读者基础和解释深度，保留通用表达标准：先讲整体作用与关系，写清对象和动作，删去重复空话，保留必要推理、条件与证据；保存来源、维护和检查要求。
- [SELF](../../../wiki/SELF.md)：写明服务对象、用途、内容边界、实际已有内容、缺口和下一步。
- [INDEX](../../../wiki/INDEX.md)：连接已有管理入口和实际知识页面，按内容组织阅读路径。
- 根目录 `LOG.md`：按共同约定追加简短操作记录，不作为固定规范。
- [wiki-ingest 说明](../wiki-ingest/README.md)与 [Skill](../wiki-ingest/SKILL.md)：在目标 Wiki 中保留“看 Wiki 的目的 → 围绕目的读材料 → 整合进 Wiki → 检查并交付”四步框架。按已确认方案先定制 README，再同步 SKILL，将整理重点与深度、来源处理、页面落点、检查及写回方式落实到对应步骤；读取、写入与复核均应用目标正文标准，共用规则引用目标的 raw 和 Wiki 规范。
- [wiki-query 说明](../wiki-query/README.md)与 [Skill](../wiki-query/SKILL.md)：轻量模式定制为 `query-<wiki-id>`，name 与目录匹配，description 写明用途与触发条件；本体自包含绑定 Wiki 绝对根目录、wiki 和 query-feedback。完整模式作为包内能力，沿用已加载入口传入绑定，不自行安装、核对版本或写反馈。创建反馈目录，不放占位 README 或虚构日志，不依赖 cwd 或临时对话。

完整模式按 [wiki-use 设计](../wiki-use/README.md)与 [执行规范](../wiki-use/SKILL.md)定制 `use-<wiki-id>` 本体，description 写明用途与接入触发条件。将选定能力的完整目录迁入本体 `skills/<能力名称>/`，包含 README、SKILL 与实际依赖，名称与目录一致；修正包内引用并同步原 AGENTS、README 及使用入口，核对迁入内容后不留独立维护副本。模板自身保留通用 wiki-query，已有轻量镜像不自动迁移或覆盖。

包内不复制知识正文、维护 Skill 或占位能力。内部 query 保留 name/目录名 wiki-query，定制用途与输入绑定该 Wiki，能力路径为 skills/wiki-query/SKILL.md，不再要求创建 query-<wiki-id> 或独立日志。创建反馈目录，准备实际 metadata：schema_version: 1、name、bindings 的 wiki_root/source_package/feedback_root、capabilities 的 name/purpose/path；source_package 指向本体。检查规范、依赖与路径后按 wiki-use 发布步骤生成递增版本及完整哈希清单，模板不预填 package.json。

在目标 AGENTS、定制后的 ingest 和 query 中写明并核对初始化后的写入边界：日常沿用已确认的项目 README、AGENTS、raw 与 wiki 规范及 Skill，不擅自改写。用户明确授权的维护任务可在范围内迭代说明、规范或 Skill 本体，检查后作为已发布版本交付；使用端只按已确认更新约定同步完整镜像并保留项目定制，一次任务开始后固定其规范版本。来源条目 README 仍按来源版本规则记录出处；内容任务可维护 INDEX 和 SELF 的覆盖、缺口、下一步，并追加 LOG 实际操作记录，用途和范围不随日常任务改变。query 只读 wiki；独立调用新增一份反馈，包内调用只交材料由入口回传，均不写 LOG；反馈不授权修复，知识更新不自动触发迭代或重装。本次条目的处理决定不自动成为长期约定。

核对目标 AGENTS、README 及其他入口的实际模式、名称和路径，指向已定制包或轻量 query；模板路径只留在模板，不能引用已迁移旧目录。

#### 轻量 query 的同内容镜像

1. 核对本体设计与执行一致、文件引用及范围，检查后作为已发布版本交付，确定 README、SKILL 与必要随包材料及实际确认的共享目录；镜像文件夹使用同一个 `query-<wiki-id>`。不复制未发布修改，不以仅复制入口或创建指向本体的链接代替完整镜像。
2. 写入前查看目标目录并比较已有镜像的相对文件清单和内容哈希。共享目录不存在同名技能时按确认范围完整安装，再核对材料齐全且逐文件相同；同名同内容时幂等跳过复制并复核绑定。
3. 同名异内容默认保留并报告冲突，只暂停镜像安装这部分，继续不受影响工作；不能凭新本体的差异覆盖旧镜像或宣称安装完成。权限或环境受限时报告具体未完成部分，不改用未经确认的位置。
4. 已明确授权更新时，依据修改本体前保存的原清单与哈希，确认镜像仍等于它原安装的已确认版本，才按本次目标、范围和更新约定完整同步检查后的已发布新版本，重新核对清单及逐文件哈希。镜像有使用方改动或旧版本依据不足时保留并报告，不猜测覆盖。

更新授权可来自用户本次请求或已确认的接入更新约定，每次升级仅限其中确定的目标和范围。知识更新不自动触发迭代或重装；query 自身不安装或同步 Skill。一次任务开始后固定其规范版本，后续更新不替换正在使用的规范。用户只要求修改模板时，用临时 Wiki 和临时共享目录验证，不写用户全局目录或其他项目。安装与校验复用现有文件工具，不引入新的初始化或安装脚本。

完整包的安装和日常使用按 [wiki-use](../wiki-use/SKILL.md) 执行，复用工具结果；知识可访问性与实际使用仍在目标环境验证。无外派请求时交付已发布本体，明确未安装。

模板其他管理文件按实际需要保留。带入 Skill 时保留执行所需文件及设计说明；携带预留设计时标明状态。知识分类根据需求与实际内容建立，所有文件引用以目标中的实际文件为准。

没有初始资料时，SELF 如实说明现状。用户明确要求处理初始资料、写入知识或增加 Skill 时，按相应需求与项目约定完成；创建或修改 Skill 使用本项目 [skill-creator](../skill-creator/SKILL.md)。

保留目标已有的 Git 历史与远程配置，初始化不向模板仓库推送用户内容。用户要求配置或发布自己的仓库时，按该项明确请求处理。

已确定的约定落实到目标文件，README 已适应该用户，SELF 和导航反映实际内容后，进入核对。

### 4. 依据评估指标核对并交付

读取定制后的文件，对照已确定方案逐项核对以下指标，并为每项结论指出对应文件、检查结果或案例判断：

| 指标 | 核对动作与达标条件 |
| --- | --- |
| 用途可执行 | 从定位说明中指出服务对象、主要任务和预期结果，用用户认可的具体场景及代表性问题说明怎样的知识或回答对用户有用。 |
| 范围可判定 | 依据已保存的核心范围、相关主题的涉及程度及范围之外的内容，说明范围内、范围外及边界案例的判断理由；重要歧义已解决。 |
| 深度有依据 | 核对目标规范保留通用表达标准，并明确读者基础和解释深度；用代表性任务及样稿检查对象的作用、整体关系和必要细节能否独立理解。 |
| 证据规则可执行 | 检查来源保存、引用与追溯约定，结合真实材料样稿核对项目要求的来源陈述、观点、推断与实际核验是否可分辨；无可用材料时使用明确标注的规则推演。 |
| 操作约定可执行 | 读取 ingest 与所选对外模式设计、执行，核对能力与维护边界；本轮要求的发布、安装及目录外使用有实际依据，可用和预留状态准确。 |
| 文件落实一致 | 对照方案核对实际模式、能力入口、链接与 INDEX，已交付镜像完整同内容；未安装状态准确，原有内容及 Git 配置保留。 |
| 后续工作可接续 | 仅依据已保存的 SELF、说明、AGENTS、定制后的 ingest 与使用入口，说明当前内容、缺口、下一项任务、所需输入、预期产物及固定文件与日常维护内容的边界。 |

同时核对 raw 来源与保存形式、Wiki 目录与页面职责、检查项是否按讨论结论写入对应规范。已有知识页面是否满足这些要求，按实际核验另行说明。

按所选模式从 Wiki 外执行代表性知识查询，记录实际读取、搜索与回答，核对未读 raw 或越界目标。轻量模式只新增一份反馈；完整模式使用方可新增安装记录、快照和反馈输入，Wiki 侧仍只新增一份反馈，知识、规范和源包未改。依据工具已核验的清单、版本、接收记录与备份交付，不重复工具核验；发布、安装与实际使用分开报告。模板验收只用临时 Wiki 和使用方目录，哈希不能证明读取边界。

镜像冲突、安装受限或目录外实际查询未完成时，分开报告本体就绪、镜像未完成及查询未验证，相关指标不能列为达标；不将本地写入或哈希相同单独当作全局安装和独立运行成功。

逐项记录结论、依据、缺口及下一步，使用以下状态：

- **达标**：满足验收条件，有可定位的文件或检查证据。
- **待补齐**：约定缺失或不完整，尚不足以指导工作。
- **未验证**：相关约定已形成，达标所需检查尚未完成。

文件检查、场景推演与真实运行分别说明。没有资料时可以用构造案例推演规则；不能把推演写成知识质量或实际运行已经通过。

发现定位或边界缺口时返回讨论；发现约定遗漏或链接错误时在范围内修正并复查。需要改变用途或范围的重要问题与用户商量。未完成必要检查的指标标记“未验证”，不提前宣布整个初始化完成。

实际初始化或约定调整结束时，在目标根目录 `LOG.md` 按日期追加一条简短记录，说明做了什么及实际结果，必要时补原因或未完成项。同任务的入库与检查汇总，不另为文件或子 Skill 记日志；不覆盖旧条目、不预填完成记录。纯讨论、拟稿与只读检查不记。回读确认本次记录与实际成果一致、用户旧记录保留，未把模板历史作为目标记录。

七项指标均有达标依据，影响用途、范围、知识要求和操作方式的关键缺口已解决，且本轮约定的交付已完成后，宣布本轮初始化完成。后续知识建设可以保留待办，知识覆盖、内容质量和实际运行结果按实际检查另行说明。

交付目标位置、实际模式与入口、选定能力、绝对绑定、逐项评估及下一步；本体、发布、安装和使用状态分开说明，附清单哈希、接收位置、备份与目录外查询结果。说明日常维护与授权迭代边界。

## 输出

讨论时交付本轮新增结论、具体方案与必要取舍，不重复已有约定；信息充分时直接推进。实施后交付定制后的 Wiki、目标位置、主要变化、使用入口及逐项评估；模拟结束交付已定约定与未验证项。

初始化完成依据第 4 步的验收结果。用户和后续 Agent 能理解用途、边界、知识要求、工作方式、实际内容与下一步。没有资料时仍可完成结构与约定的初始化；已有知识的覆盖、质量和实际运行结果单独说明。

## 校验

交付前按实际范围核对：

- [ ] 用途、边界、知识要求与操作方式明确，影响判断的重要缺口已解决。
- [ ] 可一起回答的相关问题已合并，有真实取舍时给出 2–4 个易懂选项及推荐理由；用户只回答部分时，仅补问仍影响方案的未答项。
- [ ] 用户说不清时已提供具体例子与推荐理由，并根据回答继续追问；新回答引起的理解变化已修正。
- [ ] 结束澄清有具体场景和已解决缺口作为依据，例子与推测未被当成用户结论；已明确事项、普通细节和流程过渡没有增加确认轮次。
- [ ] 已按用途与边界、raw、目录与页面、检查与工作约定的依赖组合方案，复用已有结论，只修正受新信息影响的部分。
- [ ] 页面样例前已按项目需要明确关键证据边界；普通资料整理沿用已有规则，未套用其他专业项目的评分或 AI 分析限制。
- [ ] 已主动推荐并讨论来源渠道、材料类型、原件与转录的保存形式；用户不清楚时有具体建议，取得或转录限制如实说明。
- [ ] 用途和来源方向初步明确后，已尽早读取真实材料并结合目录草案展示短样稿；没有等所有规则定稿，材料不可得时如实保留未验证项。
- [ ] 样稿的来源、依据位置和解释可分辨，用户反馈已用于调整页面与目录；讨论或模拟没有被当成写入授权。
- [ ] 本轮验收要求提前明确，七项指标有逐项结论、可定位依据、缺口与下一步。
- [ ] 代表性任务及范围内、范围外、边界案例已用于检验约定，构造案例及推演的性质说明准确。
- [ ] ingest 与所选模式设计、执行落实方案，能力已实现且完整，维护能力未默认下发；包内只有一处维护，目标入口不引用迁移前目录。
- [ ] 绑定、名称与清单一致；完整包发布、安装、实际使用分开，接收记录核对实际位置，授权更新保留定制与旧包备份。新任务一次 prepare、同任务沿用快照、结束一次 feedback，成功不重复工具核验；轻量模式保持原兼容边界。
- [ ] 目录外实际 query 未读 raw，Wiki 侧只新增一次反馈；完整模式使用方记录与知识写入分开，源包未改。静态核对、推演与实际运行分别说明。
- [ ] 日常沿用规范与授权迭代的边界已写入目标 AGENTS、ingest 与 query；新增来源、INDEX 与 SELF 现状维护、约定缺口、仅新增反馈日志和授权维护等场景已按实际验证范围核对，知识更新未触发迭代或重装。
- [ ] 文件、Markdown 链接和 INDEX 对应实际目标，用户原有内容与 Git 配置得到保留。
- [ ] 通用表达要求已落实到目标 AGENTS、正文规范与 ingest；样稿整体可理解，未靠空话或删去必要解释来压缩篇幅。
- [ ] 只报告新增结论、重要进展或阻塞；方案确定、文件写入和验收完成分别有依据，讨论或模拟未被当作实际建库。
- [ ] 文件检查、场景推演与真实运行的范围分别说明，知识覆盖和质量未被当作结构初始化的验收结果。
