# Wiki Use：通用对外能力包

本目录提供能力包入口与工具的通用模板。`wiki-init` 按具体 Wiki 的用途定制名称、绑定和内部能力，再检查并发布；未绑定、没有发布清单的模板不算可用的外派包。

## 1. 任务与设计目标

让外部项目通过一个入口使用 Wiki 的知识和已有方法。知识留在原 Wiki，应用代码和运行结果留在使用方项目，使用反馈回传给 Wiki 维护端。

入口按需读取包内 Skill，发布、安装和更新以完整包为单位。默认选用本模板已有的 `wiki-query`；其他能力只有在已经实现、适合 Wiki 用途并经确认后才加入。入库、审核、检查和规范维护能力留在 Wiki 端，不默认下发。

## 2. 使用边界

外派包命名为初始化确认的 `use-<wiki-id>`，Wiki 内本体与镜像同名。现有独立 `query-<wiki-id>` 入口仍可使用。包内 query 只读知识、不读 raw、不修改公共文件，并将反馈信息交给统一入口；独立 query 仍按原流程回传一份日志。

对 Wiki 的写入仅限 `query-feedback/` 中新建独立反馈。安装记录、任务快照、应用代码和反馈输入文件归使用方项目，不属于知识写回。反馈不授权修改知识、规范或源 Skill。

用户明确要求外派并给出接收位置时执行安装；知识查询本身不触发外部安装。规范可由授权维护任务迭代，检查后发布。镜像更新按已确认约定执行，保留项目定制，不下发未发布的改动。

## 3. 输入设计

包清单 `package.json` 保存：名称、递增版本、Wiki 根目录、源包及反馈目录的绝对绑定、内部能力的名称/用途/包内路径，以及完整载荷清单和内容哈希。名称和位置由 init 确认，工具不写死主题、项目地址或能力列表。

内部能力位于 `skills/<能力名称>/`，带入其 README、SKILL 和实际依赖；不创建占位能力。清单、安装记录和快照记录不计入载荷自身哈希。知识正文不随包复制，也不触发包版本升级。

使用方提供任务、工作区、所需输出与执行条件。入口从现有上下文取得信息，不要求用户填写固定表单。外部仓库 URL 需要先对应到可访问的接收目录，不能当成本地路径。

## 4. 原则设计

1. 完整方法放在内部 Skill，入口只选择能力并组织调用，不重复整套方法。
2. 只有清单和实际内容一致的已发布源包才能安装；用户维护端明确发布，使用端不自行生成清单认可未知改动。
3. 同名其他来源、使用方定制、版本倒退或未确认内容保留并报告。已确认的更新约定可作为授权依据。
4. 每次任务使用完整规范快照，镜像的后续更新不改变已有任务；Wiki 正文仍动态读取并记录实际依据。
5. 安装更新保留旧包备份并报告路径，不自动删除。备份保护最后校验后出现的使用方改动；清理由使用方另行决定。
6. 安装记录对应实际接收项目。跨项目复制的记录不能当作当前项目接入已确认；同版本完整内容经权威源核对后，可由明确安装请求重新建立记录。

## 5. 工作流程设计

### 发布

init 定制本体和选定能力，检查范围、依赖及路径后，用 `scripts/package.py publish` 生成发布清单；改变包材料时递增版本。模板本身不预填主题或发布版本。维护过程沿用本项目的设计确认与 LOG 约定。

### 安装与更新

读取当前包清单并执行 `status`，区分有效、过时、定制、未发布、来源不可用与来源冲突。用户明确给出目标并要求接入时，使用 `install --project` 在目标 `.agents/skills/<包名称>/` 安装完整包，并回读核验。相同内容幂等复用；干净旧镜像只有在授权更新时加 `--allow-update`。

初始化确认用户共享 Skill 目录时，使用 `install --skills-dir` 明确给出目录，不把共享目录当成项目路径。安装记录区分项目与共享位置，并核对实际接收目录。

更新先准备并核对完整新包，重新检查接收内容再替换；保留旧包备份及进行中任务快照。出现使用方改动时保留并报告。安装记录必须绑定当前接收项目；对跨项目复制且与当前发布完全一致的包，可在明确安装时刷新记录，旧包或来源不明的复制品不猜测接管。

工具返回成功后仍核对文件、安装记录、版本及知识可访问性；包安装与知识使用分别交付，不把命令发出或创建空目录称为完成。

### 使用

开始任务前完成更新判断，用 `snapshot --output` 在应用任务目录创建完整包快照，记录位置与版本并重新读取入口和所需内部规范。续接同一任务使用已有快照，不中途切换。

入口按清单用途选择能力，不默认加载全部材料。query 读取知识正文和必要关联；其他应用能力按自身执行约定使用应用代码、环境和结果目录。需要修改公共知识或共享方法时只形成反馈，交给维护任务。

### 反馈

一次应用调用结束后，入口汇总内部能力的反馈，使用快照的 `feedback --input` 新建一份日志，不由子 Skill 重复写。记录任务摘要、实际能力、已读知识位置、结果、限制及建议，工具附包版本和内容标识；不复制业务源码或完整对话。

反馈文件只在绑定 Wiki 的 `query-feedback/` 中独占创建。目录或写入受限时交付原文本并说明未回传，不改写其他位置。纯安装请求不制造知识使用反馈。

## 6. 输出设计

外派交付接收项目、完整安装路径、版本、核验结果、安装记录及 Wiki 可访问性。更新交付实际状态和保留备份位置。应用任务交付答案、方案或执行成果及其依据、使用版本和未知；反馈交付新增路径或未回传文本。

设计完成、发布完整性、临时工具验证、真实项目接入和应用实测分别说明。工具测试不证明领域知识或 GPU 结果正确。

## 7. References 与工具

执行入口见 [SKILL.md](SKILL.md)，标准库工具见 [package.py](scripts/package.py)，生命周期验证见 [test_package.py](scripts/test_package.py)。工具提供 `publish`、`verify`、`status`、`install`、`snapshot` 和 `feedback`，不依赖额外服务或第三方库。

具体 Wiki 的能力来自 init 实际选择的完整 Skill。知识入口和执行环境由已确认用途决定，不携带参考项目的主题、GPU、服务器或历史路径。

## 8. 校验设计

核对设计与执行一致、清单与全部载荷一致、包内依赖可读。用临时 Wiki/使用方目录验证实际安装、重复安装、授权更新、定制与不同来源保留、旧快照稳定、反馈独占新增及失败状态。

回归检查最后校验后出现的并发定制仍可从旧包备份恢复，以及从 A 复制镜像到 B 后安装记录对应实际项目。静态检查、工具运行和实际知识查询分别验收。只修改模板时，不安装真实项目或用户共享目录。

## 9. 文件结构

```text
wiki-use/
├── README.md
├── SKILL.md
└── scripts/
    ├── package.py
    └── test_package.py
```

初始化后的具体包另外包含发布生成的 `package.json` 与已选择的 `skills/`；它们是具体 Wiki 的实际产物，通用模板不放占位清单或能力目录。
