# Wiki Use：通用对外能力包

本目录提供入口与工具模板。wiki-init 按具体 Wiki 的用途定制名称、绑定和内部能力，再检查并发布；未绑定、没有有效发布清单的模板不是可用外派包。

## 1. 任务与设计目标

让外部项目通过一个入口使用 Wiki 的知识和已有方法。知识留在原 Wiki，应用代码和运行结果留在使用方项目，使用反馈回传给维护端。

日常使用只需三步：**prepare 准备版本 → 按需调用能力 → feedback 回传一次反馈**。工具负责包完整性、安装记录和写入核验；成功后入口直接继续，失败或结果明显不一致时才定向排查。工具成功不证明知识可达或应用结果正确。

默认选用已有 wiki-query；其他能力只有已经实现、依赖齐全、适合 Wiki 用途并经确认后才加入。入库、审核、检查和规范维护留在 Wiki 端，不默认下发。

## 2. 使用边界

外派包命名为初始化确认的 `use-<wiki-id>`，本体与镜像同名。现有独立 `query-<wiki-id>` 保持兼容。包内 query 只读知识、不读 raw、不修改公共文件，只交反馈信息；独立 query 仍自行回传一份日志。

对 Wiki 的写入仅限 query-feedback 中新建独立反馈。安装记录、任务快照、应用代码和反馈输入文件归使用方，不属于知识写回。反馈不授权修改知识、规范或源 Skill。

用户明确要求接入并给出接收位置时才安装；普通知识使用不触发安装。更新授权来自本次请求或已有接入约定；没有更新授权时不加 --allow-update。规范由授权维护任务迭代并发布，使用端不将草稿自行变成发布版本。

## 3. 输入设计

package.json 保存名称、递增版本、Wiki 根目录/源包/反馈目录的绝对绑定、内部能力名称/用途/包内路径，以及完整文件清单和内容哈希。名称和位置由 init 确认，工具不写死主题、项目地址或能力列表。

内部能力位于 `skills/<能力名称>/`，包含 README、SKILL 和实际依赖，不创建占位能力。清单、安装记录和快照记录不计入载荷自身哈希。知识不复制到包内，也不触发包版本升级。

入口从当前任务取得工作区、输出与执行条件，不要求固定表单。项目安装使用实际项目根目录，共享安装使用已确认 Skill 目录；仓库 URL 需先对应到可访问的接收目录。

## 4. 原则设计

1. 完整方法放在内部 Skill，入口只选择并组织调用，不重复整套方法。
2. 整包发布、安装和更新；只有清单与实际内容一致的已发布源包可以安装。
3. 使用方定制、其他来源、版本倒退或依据不足的内容保留并报告。
4. 每项任务使用完整快照，同任务续接不重新准备或换版本。知识仍动态读取，指令版本与实际知识依据分别记录。
5. 更新保留旧包备份并报告，不自动删除，保护最后校验后出现的使用方修改。
6. 安装记录对应实际接收类型和位置，跨位置复制不能当作当前项目的接入依据。

## 5. 工作流程设计

### 日常使用

新任务调用一次 prepare，在已有更新授权下可加 --allow-update。工具核对本地与源包、更新干净旧镜像并创建完整快照，返回 snapshot、version、content_sha256 及必要限制。没有授权时保留有效本地版本并说明限制；本地无有效发布或载荷不完整时不能声称可用。已有任务快照直接续接，不重新准备。

从所选快照读取入口和所需内部规范，按清单用途选择能力，不默认加载全部。query 读取绑定 Wiki 的知识与关联；应用能力按自身约定使用应用代码、环境和结果目录。公共知识或共享方法的修改只形成反馈，交维护任务。

任务结束时汇总内部能力信息，通过快照的 feedback --input 新建一份日志。同任务续接不重复提交；这是入口约定，task_id 不自动防止重复写入。反馈记录实际能力、已读知识位置、结果、限制和建议，工具附包版本与内容标识，不复制业务源码或完整对话。成功直接交付新增路径；失败交付原文本并说明未回传。纯安装不制造使用反馈。

### 安装与更新

明确接入时，使用 install --project 安装到目标 `.agents/skills/<包名称>/`；共享接入用 install --skills-dir 安装到确认的 `<Skill目录>/<包名称>/`。二选一，不猜全局路径。

同内容幂等复用，干净旧镜像只有授权时加 --allow-update。工具核对源包和接收内容，安装记录区分 project/shared 并核对实际位置，保留使用方定制。接收位置、来源或内容不能确认时保留并报告，不猜测接管。

更新保留旧包备份，进行中的任务沿用原快照。工具成功后依据结果交付安装路径、版本、记录与备份位置，不再重复 status、verify 或目录对比；知识可访问性仍按实际目标环境确认。

### 维护发布

init 或授权维护者定制本体与选定能力，检查范围、完整依赖和包内引用后，用 publish --version 生成发布清单。首次发布通过 --metadata 给出实际名称、绑定与能力；已有版本递增。模板不预填清单或占位能力，知识变化不升级包。

status、verify 和独立 snapshot 保留给维护与定向诊断，不是正常使用的追加步骤。维护按本项目的设计确认与 LOG 约定处理；发布不等于安装、Git 推送或应用实测。

## 6. 输出设计

先交付任务答案、方案或执行成果及知识依据，合并内部能力的重复说明，保留影响判断的条件与限制；再简述使用版本和反馈路径，回传失败时附原文本。安装任务交付实际位置、版本、记录与备份位置，知识访问单独说明，不展开无用的工具过程。

设计、发布完整性、临时工具验证、真实接入和领域实测分别报告，工具测试不证明知识结论或 GPU 结果正确。

## 7. References 与工具

执行入口见 [SKILL.md](SKILL.md)，标准库工具见 [package.py](scripts/package.py)，验证见 [test_package.py](scripts/test_package.py)。工具提供 prepare、feedback、install、publish、verify、status 和 snapshot，不依赖新服务或第三方库。

具体能力来自 init 实际选择的完整 Skill，不携带参考项目的主题、GPU、服务器或历史路径。

## 8. 校验设计

核对设计与执行一致、清单与全部载荷一致、包内依赖可读。用临时 Wiki/使用方目录验证项目与共享安装、一次准备、定制保护、接收位置、备份保留、固定快照和唯一反馈。

从 Wiki 外完成代表性知识查询，记录实际读取与回答；Wiki 侧只新增反馈，知识、规范、源包和旧日志不变。模板验收不写真实项目或用户全局镜像，临时安装不称为正式接入。

## 9. 文件结构

```text
wiki-use/
├── README.md
├── SKILL.md
└── scripts/
    ├── package.py
    └── test_package.py
```

这是通用模板。实际初始化后，具体 `use-<wiki-id>/` 再包含发布清单和选定的 skills/；通用模板不假装已有绑定或发布版本。
