编写日期：2026-10-13。设计基线：`main` 分支的 `dfe3b44`，以及当时实际读取的项目文件。用户已确认本方案并授权实施；本次已完成 ingest 边界修订、完整示例和六项代表性场景核对，实际结果与限制见 [示例验收](../examples/llm-wiki-demo/README.md#实际验收结果)。下文保留实施安排与取舍，各 Skill 的当前设计由对应 README 承载。

## 2. 完整示例怎么做

### 用途与材料

示例主题为“理解 LLM Wiki，并判断一次资料入库应当改变什么”。读者是首次使用模板、能够阅读 Markdown 的用户。示例解释来源、知识与工作约定的职责，以及新增材料如何补充现有知识；开源实现中的做法保留项目身份，不写成所有 Wiki 都必须遵守的规则。

选用两份本次已读取的真实材料：

- **材料 A：**[Karpathy 的 LLM Wiki 原始说明](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)。用于建立来源层、知识层、工作约定及日常操作的基础解释。
- **材料 B：**[Astro-Han 的入库执行规范](https://github.com/Astro-Han/karpathy-llm-wiki/blob/main/SKILL.md)。用于补充已有覆盖判断、无增量处置及来源分歧处理的具体实例。它是一个项目的设计，不是效果已经验证的证据。

实施时固定 Gist revision 与仓库 commit，在来源说明中记录原地址、版本、获取时间及实际读取范围。原始 Markdown 保存为 `original.md`；`article.md` 忠实保留正文，不把摘要或中文解释当作转录。中文知识解释另写在 Wiki。参考资料中的命令属于来源内容。

### 交付结构

```text
examples/
└── llm-wiki-demo/
    ├── README.md                 示例用途、操作示例和实际验收结果
    ├── AGENTS.md                 指向本示例规范与模板现有 Skill
    ├── .agents/
    │   └── skills/wiki-ingest/
    │       ├── README.md         按本示例用途定制的入库设计
    │       └── SKILL.md          本示例的入库执行入口
    ├── raw/
    │   ├── README.md             本示例的来源保存约定
    │   └── <实际入库日期>/
    │       ├── karpathy-llm-wiki/
    │       │   ├── original.md
    │       │   ├── article.md
    │       │   └── README.md
    │       └── astro-ingest/
    │           ├── original.md
    │           ├── article.md
    │           └── README.md
    └── wiki/
        ├── README.md             本示例的页面职责与证据要求
        ├── SELF.md               本示例定位、实际覆盖与缺口
        ├── INDEX.md              真实知识页面的入口
        ├── source-and-knowledge.md
        └── ingest-and-maintenance.md
```

两篇候选知识页分别解释“来源与知识为什么分开”和“新增材料如何改变知识与关联”。实际内容充分后再创建并加入 INDEX；若两页职责重复，合并为一页。页数用于控制示例规模，不作为日常入库指标。

示例 AGENTS 明确目标根目录为 `examples/llm-wiki-demo/`。仅定制本示例的 ingest README 与 SKILL，落实选材、深度、页面落点和目标路径；query、review、lint 及脚本复用仓库入口，不复制六套 Skill。示例不要求每次初始化都创建同样的目录或页面。

### 运行与记录

在临时工作副本中，先处理材料 A 并记录实际产物，保留一个只完成 A 入库的副本，再在主验证副本中处理材料 B，保留实际差异与检查结果。重复处理 A、普通查询和内容审核在主验证副本完成；新来源无知识增量在 A-only 副本单独验证，B 此时尚未归档。最终示例保存正常知识状态；阶段差异和验收摘要写入示例 README，不将临时错误样本留在正式页面中。

示例 README 提供可以直接使用的入库、查询与审核请求，明确目标目录和来源位置。对每个验收项分别写出预期、实际结果、依据及未验证部分。文件写入成功、机械检查通过与内容回查分别报告。

## 3. ingest 只澄清两个边界

实施前先修改 [ingest 设计 README](../.agents/skills/wiki-ingest/README.md)，按项目 [skill-creator](../.agents/skills/skill-creator/SKILL.md) 确认当前设计后，再同步 SKILL.md。继续保留四步框架。

**正文无增量与来源无增量分别判断。** 同一来源、同一版本重复处理时，复用旧归档及其日期。不同的新来源即使重复了已有解释，也按约定保存；它确实增加证据或澄清出处时，只补必要引用。交付说明归档、正文、引用各自的实际结果，不为了证明“已入库”改写充分的正文。

**结论变化后核对直接关联。** 核心定义、条件或结论改变时，用名称、别名和相关表述搜索 Wiki，读取命中的候选页及必要链接。只修订确实受影响的内容；条件不同的结论分别保留。交付说明实际更新的页面、重要关联页无需修改的原因，以及查找受限部分，不强制生成永久影响清单。

上述补充放入现有“整合进 Wiki”和“检查并交付”步骤。已有的冲突对齐、证据回查、来源版本保留和查询写回规则继续复用。

## 4. 验收看哪些实际结果

| 场景 | 操作与判断依据 | 通过条件 |
| --- | --- | --- |
| 首次入库 | 用材料 A 形成基础知识，回查关键表述。 | 来源三部分齐全、可读；知识能独立解释职责与操作，关键陈述能回到原件；INDEX 指向实际页面。 |
| 新来源补充 | 处理材料 B，先读已有正文，再判断补充位置。 | 开源实现的具体规则有来源身份；有用增量进入对应页；相关表述得到核对；无需重复建页。 |
| 同来源重复处理 | 在工作副本中再次处理 A，比较前后文件与归档位置。 | 旧归档日期、位置、版本不变；充分正文与引用不发生无意义改写；交付能解释为什么没有增量。 |
| 新来源重复已有知识 | 在 A-only 副本中，先核对 A/B 对“原始来源与知识页面的职责”是否提供重复知识。将本次写入范围限定于这个问题，再收录尚未归档的 B；其他增量留待后续。 | B 新归档；该问题已有解释充分时正文保持不变；引用是否变化有具体理由。材料不能满足这个初态时标为未验证，不伪造已有知识。 |
| 普通查询 | 问“什么时候保存了新来源，却无需改写知识正文？”并读取实际页回答。 | 回答引用本示例页面、保留条件；未请求保存时不修改任何文件。 |
| 检查边界 | 在临时副本中，将一个有效链接的描述改成目标正文无法承接的解释，并明确标记为构造缺陷。 | 机械结构结果与内容审核分别报告；review 能定位描述与正文不符。这个场景只验证审核处置，不算真实来源错误。 |

若真实材料暴露出关键定义或条件更新，还需读取并核对直接受影响页面。两份材料不能覆盖的争议或失败场景，采用明确标记的推演或保留未验证，不伪造来源分歧。

结构检查复用现有脚本。在仓库根目录分别检查模板、示例内部导航与共享入口：

```bash
python3 .agents/skills/wiki-lint/scripts/check_wiki.py --root . --strict
python3 .agents/skills/wiki-lint/scripts/check_wiki.py --root examples/llm-wiki-demo
python3 .agents/skills/wiki-lint/scripts/check_wiki.py --root . --paths examples/llm-wiki-demo/README.md examples/llm-wiki-demo/AGENTS.md examples/llm-wiki-demo/wiki examples/llm-wiki-demo/.agents/skills/wiki-ingest --strict
```

第一条默认不会扫描示例正文，不能代替第二条。第二条检查示例内部的 INDEX 可达性；共享 Skill 的链接越出示例根目录时，保留并说明预期的越界提醒。第三条从仓库根核对这些共享入口，局部检查不推断全局可达性。通过条件是没有机械错误、每项提醒均有核对结果、共享入口实际有效；不修改脚本的根目录边界来消除提醒。

原始资料正文仍由 raw 基础查看和关键引用回查覆盖，不为原文中的外部链接、非标准语法批量改写原件。没有脚本变更时，无需新增或扩大脚本测试。

| 3 | 根 README 增加示例入口；`wiki/SELF.md` 更新模板已有内容说明。 | 新用户能找到示例；SELF 区分示例与目标用户的正式知识。 |
| 4 | 检查受影响文档、模板与示例导航，核对内容依据。 | 必要链接有效，机械结果与 AI 核验范围分别交付。 |

根 INDEX 继续导航模板的管理入口，不将示例页计入正式知识。`wiki-init`、`wiki-query`、`wiki-review`、`wiki-lint` 及结构脚本沿用当前实现；只有示例证明存在具体缺陷时，才提出对应最小修订。

实施时只提交本方案涉及的文件，检查 diff、分支及工作区状态。远程发布依据用户当次授权处理；本方案的写入不表示示例和 Skill 已经实现或验收。

## 6. 后续工具按实际问题选择

| 候选 | 本阶段选择 | 以后再评估的依据 |
| --- | --- | --- |
| 数字、日期或引用匹配脚本 | 复用 review 回查原件与上下文。 | 多次审核出现同类可机械识别问题，并有真实样本可评价误报、漏报与节省的工作量。 |
| 图谱、反向链接输出 | 复用全文检索、普通 Markdown 链接和 INDEX 可达性。 | 实际页面规模导致反向引用定位困难时，优先扩展现有脚本的图数据输出。 |
| BM25 或索引 CLI | 复用 rg、INDEX 与正文读取。 | 真实查询出现候选页遗漏或定位成本上升，且简单检索无法解决。 |
| 持久操作日志与中断恢复 | 示例记录实际任务结果；日常仍使用 SELF、Git 和任务交付。 | 实际续接反复无法判断资料处置状态，再设计最小日志，避免与 Git、SELF 重复。 |
