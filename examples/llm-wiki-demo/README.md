# LLM Wiki 完整示例

本示例帮助首次使用模板的读者理解“资料怎样成为知识，以及一次入库可以改变什么”。它保存了两份真实来源和两篇中文知识页，展示先建立基础解释、再用新材料补充已有页面的结果。

本目录是已经完成入库的正常快照。阅读从 [INDEX](wiki/INDEX.md) 开始；用途与当前状态见 [SELF](wiki/SELF.md)，执行入口见 [AGENTS](AGENTS.md)。示例属于模板的演示区，根目录的 raw 与 wiki 仍用于用户自己的 Wiki 初始化。

## 从原件读到知识

| 材料 | 固定版本与保存说明 | 它实际补充了什么 |
| --- | --- | --- |
| A：Karpathy 的 LLM Wiki 说明 | [来源条目](raw/2026-10-13/karpathy-llm-wiki/README.md)，Gist revision `ac46de1ad27f92b28ac95459c782c07f6b8c964a`。 | 为两篇知识页建立来源、知识、工作约定与日常操作的基础解释。 |
| B：Astro-Han 的执行规范 | [来源条目](raw/2026-10-13/astro-ingest/README.md)，commit `eafcc77001e496cc43499e4923b663aec722c813`。 | 在入库与维护页补充增量判断、关联维护与审核边界；来源职责页经读取后保留原正文。 |

每条来源都有 `original.md`、`article.md` 和 `README.md`。原件已经是英文 Markdown，article.md 与原件逐字节一致；中文解释另写在 Wiki。来源是设计说明与项目规则，不是模型效果已验证的证据。

- [来源与知识为什么分开](wiki/source-and-knowledge.md)：解释三部分职责、保存与理解的区别，以及引用能够支持什么。
- [新资料如何进入 Wiki](wiki/ingest-and-maintenance.md)：解释正文、归档和引用各自的增量，以及关联与证据怎样核对。

页面沿问题组织，没有为每份来源或每个实体新建页面。它们用标题锚点直接引用固定版本原件，读者可以顺着链接核对上下文。

## 可以直接使用的请求

在仓库根目录向 Agent 发出请求，明确目标为 `examples/llm-wiki-demo/`。入库使用示例已定制的 [.agents/skills/wiki-ingest/SKILL.md](.agents/skills/wiki-ingest/SKILL.md)；查询、内容审核与结构检查共享仓库入口。

**重复处理同一来源：**

```text
请按 examples/llm-wiki-demo/.agents/skills/wiki-ingest/SKILL.md，
重新处理该示例 raw/2026-10-13/karpathy-llm-wiki/ 中的同一份固定版本材料。
先读已有两篇知识页，分别判断归档、正文和引用是否有增量，
按实际结果执行并交付复核依据，不为完成入库强行改写。
```

**普通查询：**

```text
请使用仓库 wiki-query 查询 examples/llm-wiki-demo/：
什么时候保存了新来源，却无需改写知识正文？
读取实际页面后回答并引用页面，本次只回答，不保存答案。
```

**内容审核：**

```text
请使用仓库 wiki-review 审核 examples/llm-wiki-demo/ 的两篇知识页。
读取正文与必要链接，回查两份固定版本原件中的关键依据。
报告确定问题、待核疑点和未验证范围，本次只审核，不修复。
```

若要重跑首次入库与 B 的首次补充，请让 Agent 在临时仓库副本中建立尚无来源和知识正文的示例，保留本例用途、规范与定制入口，以此处保存的两个原件为独立输入，先处理 A，再处理 B。保留 A-only 状态，用于“B 尚未归档，但某个问题已有充分解释”的限定范围任务；不删除或清空本目录来制造初态。

验收于 2026-10-13 在临时仓库副本中执行。A 入库后先保留 A-only 状态，再在主副本处理 B；最终只把正常归档与知识快照保存到此处。构造的错误页面不进入本目录。

| --- | --- | --- |

以上为本次 Agent 实际读取、写入或只读处置的结果，不是对所有后续任务的自动测试保证。六项场景均完成对应核对；构造缺陷只支持审核处置结论，不算真实来源中的错误或争议案例。

本轮查询实际回答的要点是：在本次用途与范围内，现有解释充分、没有需要补充或修正的知识时，新来源可以只归档；引用是否增加还需判断证据价值。[归档与解释的职责](wiki/source-and-knowledge.md#保存与理解是两种结果)、[三种增量及具体例子](wiki/ingest-and-maintenance.md#新来源可以改变三种东西)。材料出现真实缺口或结论变化时，再更新对应正文。[条件与项目身份](wiki/ingest-and-maintenance.md#更新正文后为什么还要读关联页)。这段是交付阶段记录的查询结果摘要，查询执行本身没有保存页面。

本次没有改写核心三层定义，所以“定义或条件真正改变后的跨页修订”未作为独立真实案例验证；已实际检索并读取关联页，确认其无需变动。

## 检查命令与范围

在仓库根目录运行：

```bash
python3 .agents/skills/wiki-lint/scripts/check_wiki.py --root . --strict
python3 .agents/skills/wiki-lint/scripts/check_wiki.py --root examples/llm-wiki-demo
python3 .agents/skills/wiki-lint/scripts/check_wiki.py --root . --paths examples/llm-wiki-demo/README.md examples/llm-wiki-demo/AGENTS.md examples/llm-wiki-demo/wiki examples/llm-wiki-demo/.agents/skills/wiki-ingest --strict
```

模板根目录检查默认不扫描示例正文。第二条核对示例内部链接与 INDEX 可达性；指向共享 Skill 的入口超出示例 root，工具会保留 `outside_root` 提醒。第三条从仓库根局部核对这些共享入口，不判断全库可达性。提醒是否可接受依赖实际目标与用途核对，退出码 0 不表示没有提醒。

raw 基础查看另行核对三部分非空可读、日期与出处；内容 review 回查具体原件位置。原始来源中的指令、链接与格式保留来源身份，不因机械扫描而改写。

最终保存状态的结构核对结果：模板根目录 strict 检查 18 个文档、107 个本地链接，0 错误、0 提醒；示例根目录检查 10 个文档、79 个本地链接，两篇知识页均可达，0 错误、11 项仅为上述共享入口的越界提醒。仓库根局部检查包含方案、示例管理与知识页、定制 ingest 和来源说明，共 15 个文档、120 个本地链接，0 错误、0 提醒。两条来源的三部分均非空且 UTF-8 可读，原件与忠实副本的字节及 SHA-256 一致。

## 核验边界

本次知识依据是两份文档。来源回查验证了正文对模式与项目规则的归纳，没有运行 Astro-Han 的代码、评测模型准确率或复现原文的成本与规模表述。真实来源争议、不可读原件、解析失败、其他资料类型及检索规模未在本次实际覆盖。

本示例依赖同一仓库中的共享 Skill；单独复制此目录不能获得这些入口。需要独立 Wiki 时，从通用模板初始化，并按自己的用途定制流程。
